## Context

After FC-019 shipped, the per-symbol scorecard correctly reconciles to actual cash flow — sum of Total P&L across symbols ≈ account growth (within fees + unrealized + Alpaca-side anomalies). But the per-cycle drilldown (the Symbol Deep Dive page's cycle table) still produces wrong numbers when **multiple put assignments happen on the same underlying before any are called away** (overlapping share lots).

Current pairing logic in `wheel_cycles_from_activities`: each `assigned_put` is paired to the EARLIEST subsequent `called_away` on the same underlying via `ROW_NUMBER() OVER (PARTITION BY put_activity_id ORDER BY call_outcome_time ASC)`. With two puts assigned before one called-away:

- Put #1 (Lot B, Jan 10 @ $212.50) → pairs to the only available call (Apr 17 @ $252.50).
- Put #2 (Lot C, Jan 31 @ $245) → also pairs to the SAME called-away.

Both cycles then aggregate OPTRD events from a window that overlaps the second assignment, producing inflated `capital_gain` for one cycle and treating the other as still open even though shares should have closed it.

Per-symbol totals are unaffected because the scorecard's `share_side_agg` CTE sums OPTRDs once per underlying. But the cycle drilldown shows confusing numbers.

**Concrete AMD breakdown:**
| Cycle | Put | Called-away | View `capital_gain` | True OPTRD net |
|---|---|---|---:|---:|
| 1 | 2025-11-22 @ $230 | 2025-11-29 @ $192.50 | -$3,750 ✓ | -$3,750 |
| 2 | 2026-01-10 @ $212.50 | 2026-04-17 @ $252.50 | **-$20,500 ✗** | should be +$4,000 |
| 3 | 2026-01-31 @ $245 | (mis-paired to same as #2) | +$750 ✗ | should be -$24,500 (open) |

The view's per-cycle math sums to AMD's correct total (-$24,250 ≈ -$3,750 -$20,500 +$750), but each cycle row is individually misleading.

## Goals

- Each row in `wheel_cycles_from_activities` represents **one share lot**: an OPTRD-buy paired to its OPTRD-sell.
- `capital_gain` is computed from **actual OPTRD prices** (`(sell_price − buy_price) × qty × 100`), not from `(call_strike − put_strike)`.
- Lots without a matching sell remain "open" (`call_outcome IS NULL`) and surface in the table as in-flight.
- Per-symbol totals continue to reconcile — sum of cycle `capital_gain` = `share_side_pnl` from the scorecard.

## Non-goals

- Not changing the per-symbol scorecard (`fc018_per_symbol_scorecard`). It already reconciles via OPTRD sum.
- Not changing the option-side aggregation (`cycle_call_net_realized`, `total_premium`). Those are correctly tied to the cycle window post-FC-019.
- Not addressing the Alpaca-side data anomaly where AMD's OPTRDs net to +100 shares but `/v2/positions` reports 0. That's an account-data issue, not a pairing-logic issue.
- Not back-filling option events to lots. The cycle drilldown still groups all calls within the cycle's time window — that's the right model for "everything that happened while we held these shares."
- No FIFO semantics for option events (early closes), only for share lots. Options are already paired correctly via `trades_with_outcomes`.

## Proposed approach

Two implementation paths considered. Decision: **Python-side walk** in `BigQueryService.get_wheel_cycles_for_symbol` rather than a SQL-only rewrite.

### Why Python over SQL

A FIFO walk is naturally a stateful loop: maintain an open-lots queue, append on buys, pop-and-emit on sells. SQL can express this via either:

1. **`ARRAY_AGG` + offset matching** — sort buys and sells separately, pair by index. Works only if buy/sell counts match. Fragile when one side is shorter (open lots).
2. **JavaScript UDF** — write the walk imperatively in JS, run inside BQ. Heavier infrastructure; UDFs are stylistically out of pattern for this repo (no other UDFs).
3. **Recursive CTE** — possible but baroque for a forward walk.

Python in the dashboard backend is straightforward, easy to test, and the dataset is tiny (<100 OPTRD events ever per symbol on this account). Trade-off: the BigQuery view stops being a single-source-of-truth for cycle math; the backend method becomes the authoritative computation.

### Algorithm

For each symbol selected on the drilldown page:

1. Query `trades_from_activities` for all `OPTRD` events on this underlying, sorted by `transaction_time` ascending.
2. Walk events in time order, maintaining a `FIFO` queue of open lots:
   - **Buy event** (qty > 0): push a lot `(buy_time, buy_price, qty, opasn_link, put_strike, put_premium)` to the queue. Look up the matching `OPASN` activity in `trades_with_outcomes` (same underlying, same `group_id`) to get the originating put's strike + premium.
   - **Sell event** (qty < 0): pop the oldest lot. Emit a closed cycle row with both ends. If the sell's qty is larger than the popped lot, split — pop the next lot too (handles partial-call-on-multi-lot cases).
3. After the walk, any remaining queue entries become "open cycle" rows.
4. For each closed cycle: aggregate the option-side P&L (call premiums sold during the cycle window: `[buy_time, sell_time)`) by joining `trades_with_outcomes` filtered to calls within that window.

### Returned shape (unchanged from FC-019)

The existing `CycleRow` interface in the frontend stays the same. The semantic of `capital_gain` changes from "approximation from strikes" to "actual cash from OPTRD prices." `total_premium` continues to mean `put_premium + cycle_call_net_realized`. The new column would be:

- `lot_buy_optrd_id` — the OPTRD activity_id of the share-acquisition event
- `lot_sell_optrd_id` — same for the share-disposition event (NULL if open)

These let an interested user trace the cycle back to source events.

- Existing cycle table component on the frontend.

## Risks & mitigations

- **Risk:** the FIFO assumption is wrong for some edge cases (e.g., partial fills, broker-side LIFO accounting).
  - *Mitigation:* the algorithm handles partial sells by popping multiple lots. For broker accounting, the user is the only consumer and FIFO matches retail intuition. If we ever expose to multiple users with different tax-lot preferences, revisit.

- **Risk:** the AMD-style data anomaly (OPTRDs net to non-zero but Alpaca reports 0) breaks the walk.
  - *Mitigation:* the algorithm doesn't try to reconcile to Alpaca's live position count. It just pairs what OPTRD records. Open lots stay open; the drilldown labels them "Open" and notes the unpaired buy event. Users can spot the anomaly.

- **Risk:** moving cycle math out of the view weakens the SQL-as-source-of-truth pattern.
  - *Mitigation:* the view stays valid for the simple per-OPASN case if we keep it (or it gets retired). Document the trade-off in the method docstring. The data layer (FC-012/FC-019) remains SQL-driven; only the cycle pairing moves.

- **Risk:** Python implementation is harder to ad-hoc query from BigQuery (e.g., for analytics notebooks).
  - *Mitigation:* if needed later, expose a parallel SQL view. For now, the dashboard is the only consumer.

## Rollout

1. Implement and unit-test the Python FIFO walk against fixture data covering: simple 1-buy/1-sell, overlapping lots (AMD's case), partial sells, and unpaired buys.
2. Wire `get_wheel_cycles_for_symbol` to use the walk. Keep the old SQL view in place for now.
3. Deploy. Manual verification via `/v2/symbol/AMD` showing three rows: two closed lots (correct gain/loss) plus one open lot.
4. Once confirmed correct, deprecate or rewrite the SQL view in a follow-up commit.

**Rollback:** revert the BigQueryService method change. The SQL view continues to work as before, surfacing the FC-019 per-OPASN behavior.

## Open questions

- **SQL view: rewrite or retire?** The simpler answer is to retire the SQL view and have the Python method be authoritative. But retiring removes ad-hoc SQL queryability. Defer the decision to plan execution after seeing how the Python code feels.
- **Should partial sells split a lot?** Today all OPTRD events on this account move 100-share blocks. A future scenario where a single called-away takes 50 of 100 shares is possible. Algorithm should handle it. Edge-test it.
- **What about unpaired sells?** OPTRD-sell with no preceding buy on this symbol. Shouldn't happen — would imply selling shares we never bought. Treat as a data error; log a warning, exclude from cycles.
- **Display "Open" cycles in the cycle table?** They have `capital_gain = NULL` and `call_outcome_time = NULL`. Worth showing? On AMD this would surface the unaccounted lot as a visible "open since 2026-01-31, no called-away" row. Probably yes — it's diagnostic.
