## Context

FC-065 was filed as "port FC-029's drawdown pause to the production path." Three investigations (mechanism inventory, floor economics, lifecycle coherence) show that framing is too narrow: the pause is one symptom of a structural condition, and patching it alone would add a **fifth** guard to a layer that already has four cost-basis floors on two code paths.

**What the investigations established:**

1. **Production runs a stateless wheel.** Phase is emergent from Alpaca positions + BigQuery history. The codebase maintains a parallel *stateful* wheel (`WheelStateManager`, phases, premium accumulators, roll counts) that is rebuilt per request and discarded — `STATE_STORAGE_BUCKET` has never been set. Nearly every defect in the FC-029/038/045/048/050/062/065/066 family is a control installed on the fictional half.
2. **The drawdown pause has a silent substitute.** On the live path, an underwater position quietly yields nothing: below-floor strikes are rejected as `below_cost_basis` (the floor check runs *before* delta — `market_data.py:447`), and the above-floor strikes that survive it fail the delta/premium bands. Same outcome as a pause, with no event saying "paused," no threshold to tune, and no escalation hook. Verified: every NVDA scan since 07-30 ends `stage_8_complete_not_found` with `rejected_delta_out_of_range: 0` — nothing even reaches the delta check above the floor. *(Mechanism sentence corrected on review — the conclusion stood, the attribution didn't.)*
3. **The floor value is correct today but has never had a stated rationale — and the sources beneath it disagree.** FC-050 (shipped 07-30) made the floor the **assigning-put strike**, inherited from FC-029's chain without the value ever being chosen. An economic analysis of all 16 lots and 88 call writes initially recommended loosening it to the broker's premium-adjusted basis (strike − put premium), on the grounds that it is the loosest floor still guaranteeing cycle-net ≥ 0. **That recommendation was rejected on review (2026-07-31), and the rejection is now the plan's governing principle** — see "The floor definition, decided" below.
4. **Four live defects nobody had catalogued**: every production `call_sale_executed` logs `shares_covered=0, stock_cost_basis=0, total_return_if_called=0` (the *fourth* instance of the untyped-shape root cause); `wheel_cycles` holds 36/30/6 duplicate zero-gain rows per assignment; the floor's BigQuery source is age-bounded to 90 days so it **silently reverts** to Alpaca basis (AMZN/GOOGL age out 2026-09-04, NVDA 09-07, AAPL 09-11) with no event; and call limit pricing (`mid × 0.95`) never received the put side's spread-aware improvement.
5. **The backtest measures a strategy nobody trades.** The simulator replays `run_strategy_cycle` — the dead engine path — which has a drawdown pause, phase gating, single-candidate selection, and no committed-share accounting. Production has none of those and has extra ones the backtest lacks.

**The through-line:** where the Symmetry Principle could be enforced by code proximity it held; where it required carrying a change across files it broke every time. That argues for structural enforcement, not more review discipline.

## Goals

- **One floor value: Alpaca's `avg_entry_price`** — broker-authoritative, verifiable in the UI, automatically weighted across lots. Below it we hold uncovered until recovery rather than writing calls, so collected premium stays profit instead of subsidizing a flat exit.
- **One floor implementation.** Every order-placing path resolves the floor through `CostBasisResolver` and passes the same gate. No path fails open.
- **Regime protection on the path that trades**, as an explicit, tunable, observable decision rather than an emergent side effect of the delta band.
- **A legible decision record**: for any symbol on any cycle, a durable answer to "did we sell a call, and if not, why not."
- **One candidate-generation path**, so what the backtest measures is what production does — *delivered by FC-068 (split from this plan), which this plan unblocks via Phase 3*.

## Non-goals

- Changing the delta band, premium floor, DTE target, or any filter threshold (FC-029/FC-034 territory).
- Permitting below-floor writes on underwater positions — that is a real policy question with real money attached (≈ **$130/week/lot** foregone on NVDA today), but it is **FC-033's** scope and it now has the numbers it was waiting for. Explicitly out of scope here.
- Wheel-state persistence (FC-039). This plan assumes it stays dead and derives from durable sources instead.
- The roller's revival (FC-066). Phase 2 fixes the roller's *floor* (satisfying FC-062's floor half); reviving the roller remains separate.
- Backfilling or correcting historical data (`wheel_cycles`, `trades` labels — FC-067, and the spin-off below).

## Proposed approach

### The floor definition, decided

**The floor is Alpaca's reported `avg_entry_price` for the equity position. One field, broker-authoritative, operator-verifiable in the Alpaca UI.**

**The principle it serves:** never write a call that locks in a loss against what we hold, and never spend collected premium to subsidize a flat exit. Below the floor we **hold the shares uncovered until they recover, then resume writing calls** — premium stays profit rather than becoming a discount on the exit.

**One honest caveat, deliberately accepted.** Alpaca's `avg_entry_price` is *premium-netted*: it reports the assignment price minus the put premium. Verified on AAPL — assigning put `AAPL260612P00305000` sold for $1.50, assignment bought 100 shares at $305.00 (`net_amount −$30,500`), Alpaca reports **$303.50**. Same on all four lots (AMZN 262.50→261.20, GOOGL 370.00→368.34, NVDA 220.00→218.43). So the floor sits one put premium below the cash actually paid.

**Why that is acceptable, with evidence:** the gap is $1.30–$1.66 while strike increments on these underlyings are $2.50, so **no tradeable strike falls inside the gap** — verified against live chains for all four positions (AAPL `[302.50, 305.00, 307.50]`, none in `[303.50, 305.00)`; same result for AMZN, GOOGL, NVDA). Both definitions admit an identical strike set. The simplicity is free today.

**The condition that would make it bite is ALREADY LIVE — corrected on review (2026-07-31).** The trader reviewer found the "no strike in the gap" predicate false for the pipeline as a whole: **IWM trades on a $1 strike grid**, is the most active put underlying in the book (16 put fills in July, one prior assignment 2026-03-13), and has an open 285P right now. Two puts held this week would have had tradeable strikes inside their gaps on assignment (`IWM260803P00287500` @ $1.05 → 287.0 in-gap; `IWM260806P00283000` @ $1.45 → 282.0 and 282.5 in-gap, strikes verified live). So on a normal-premium IWM assignment, this floor permits a strike below cash-paid — bounded (cycle-net stays ≥ 0; worst case ≤ one put premium ≈ $50–150/lot), but a standing exception to the governing principle, arriving weekly, not a hypothetical.

**Control (replaces "revisit if the universe changes", which had already failed unnoticed):** an **assignment-time gap audit** — on every new lot, compute `[avg_entry, assigning strike)`, enumerate chain strikes inside it, and record the result in the decision record (Phase 4) with a warning event when non-empty. Whether in-gap strikes are then *permitted* (bounded loss vs cash-paid, cycle-net ≥ 0) or *blocked* (floor = assigning strike for that lot) is **Open Question 1 — operator decision.**

**Alternatives considered and rejected:**

| Definition | Verdict |
|---|---|
| **Alpaca `avg_entry_price` (adopted)** | Broker truth, one field, no derivation, averages multiple lots automatically, visible in the UI. Premium-netted by ~0.5%, currently immaterial |
| Cash actually paid, reconstructed from acquisition rows | Matches the principle exactly, but requires BigQuery reconstruction, a lookback window, and bespoke multi-lot averaging — complexity with no tradeable difference today |
| Net-of-cycle / ACB-style (basis − all premium collected) | **Rejected, and it is the dangerous one.** Path-dependent and ratcheting: in the AMZN chain it fell 246.38 → 224.53 as roll-down premium accrued, so collected premium becomes license to lock in ever-lower strikes — a few more weeks and it would have *permitted* the −$3,500 disaster. It is the right **scorekeeping** number (the FC-024 ACB views) and the wrong **guard**. Extreme case: NVDA's lifetime ACB is $156.79 against a $220 lot |
| Premium-offset (allow if strike + this call's premium ≥ basis) | **Rejected** — same erosion, one step further removed |

**At-floor writes remain allowed.** A call struck at the floor keeps both premiums and gives up no capital — genuinely profitable. GOOGL's 370C is correct behavior, not an edge case to close.

**Multiple lots** are handled by Alpaca's own weighted average, which is exactly the semantic we want and removes the need for bespoke lot arithmetic.

### Phase 1 — Invert the resolver: Alpaca is the floor, BigQuery is the cross-check

Today's `CostBasisResolver` chain is `wheel_state → BigQuery OPASN strike → Alpaca`, with Alpaca last. Invert it:

- **Primary and only floor source: Alpaca `avg_entry_price`** for the equity position. **Plumbing (BLOCKER caught at plan review): `AlpacaClient.get_positions()` strips this field today** (`src/api/alpaca_client.py:244-259` returns only symbol/qty/side/market_value/cost_basis/unrealized_pl/asset_class), and `BacktestAlpacaClient.get_positions` never emits it — as originally written, Phase 1 would have failed closed fleet-wide while unit tests passed on a fixture that happens to carry the field. **Both clients must emit `avg_entry_price`, with a contract test asserting it against the wrapper's REAL output shape, not the conftest fixture.** (For long positions it equals `cost_basis/qty` — verified on all four lots — which is the fallback derivation if the SDK field is ever absent.)
- **Fail closed** if it is absent, zero, or the position cannot be read — the existing fail-closed scanner skip (`call_scan_skipped_cost_basis_unresolved`, added by FC-038 and labeled FC-050 in code at `options_scanner.py:146-158`) already implements this; keep it, and **wire that event to the alert channel**: a recurrence of FC-029's zero-basis behavior would starve the entire book (every wheel position is an assigned position), and today nothing alerts on it.
- **BigQuery is demoted to a divergence cross-check with teeth — it runs inline, per held symbol, per scan, and fail-closes the symbol on divergence.** Both reviewers independently rejected warn-only ("a warning nobody reads is not a control"; the dangerous case is *presence with a wrong value* — e.g. a mis-adjusted split — which fail-closed-on-zero cannot catch). Consequences accepted explicitly:
  - The per-symbol BQ query **stays on the scan path** — its role changes from floor-setter to floor-verifier. The `/scan` latency therefore stays ~25s, already recorded as acceptable in FC-050. (The earlier claim that latency would return to baseline is withdrawn — it contradicted the cross-check having teeth.)
  - **Derivation, specified:** cash paid = OPASN `strike × 100` (OPASN rows carry no price — verified NULL); expected `avg_entry` = strike − premium, where premium is the last sell-to-open FILL of the assigned contract before assignment (roll/re-sell ambiguity resolved as "last fill"; if underivable, no comparison is possible — log that, keep the floor, fail closed only on zero/missing). Multi-lot: weighted across OPASN rows for currently-held quantity; if reconstructed shares ≠ Alpaca qty, treat as divergence.
  - **Tolerance:** `max($0.10, 0.1% of basis)` against the expected value. Beyond it → `call_scan_skipped_cost_basis_divergent` (new event, alerted) and the symbol is skipped for that scan.
  - **Stated blind spot:** if both sources are stale the same way (e.g. Alpaca unadjusted *and* BQ history pre-split), they agree on the wrong number and the cross-check is silent. No cheap third source exists; accepted, recorded.
- **`wheel_state` is removed from the chain entirely.** It has never been populated in production (`STATE_STORAGE_BUCKET` unset since inception) and its presence has misled three separate investigations into believing a live source existed.
- **Interim backtest semantics (until FC-068), stated:** the simulator's floor becomes the adapter's `avg_entry_price`; the backtest broker sets assignment basis = strike (`broker.py:402-412`), not premium-netted, so the backtest floor sits one put premium above production's for the interim window. Accepted in writing here; FC-068 closes it.

**Test contracts this phase deliberately inverts (enumerated — the honesty the revert owes):** FC-050's mutation-hardened `test_a_bigquery_hit_beats_a_positive_alpaca_basis` and `test_wheel_state_beats_a_positive_alpaca_basis_too` (precedence flips by design — these must be *rewritten to pin the new order and re-mutation-tested*, not deleted); the resolver source-order tests in `test_cost_basis.py`; the R2 subset of the 27 FC-029 chain tests (resolving the conflict with FC-068's "migrate, not delete": the R2-chain tests are **rewritten here** against the inverted resolver; FC-068 migrates the remaining engine-path guard tests). The conftest hermeticity guard patches `CostBasisResolver._lookup_last_opasn_put_strike` — the cross-check must keep that method as its single BQ chokepoint so tests cannot reach live BigQuery.

**What this dissolves, at no cost:**

- **The 90-day cliff disappears.** It only existed because the BigQuery lookback was a *floor* path; as a cross-check, an aged-out window degrades to "no comparison available," not to a silently looser floor. Removes the dated hazard (AMZN/GOOGL 2026-09-04, NVDA 09-07, AAPL 09-11).
- **FC-064's mixed-lot problem dissolves.** Alpaca's `avg_entry_price` is already a weighted average across lots — the exact semantic wanted — so no bespoke lot arithmetic is needed and `max(BQ, broker)` becomes moot.
- **Two of FC-029's three sources stop setting the floor.** (The per-scan BigQuery query remains as the inline cross-check — see above — so `/scan` latency stays ~25s; that cost was already recorded as acceptable in FC-050.)

**Net effect on today's live book:** floors move from 305.00/262.50/370.00/220.00 to 303.50/261.20/368.34/218.43 — and **the tradeable strike set does not change**, verified against live chains (no strike falls in any of the four gaps). The acceptance test is that the set of qualifying strikes per symbol is identical before and after.

**Risk this phase must retire:** FC-029 (2026-05-08) reported that Alpaca returns `cost_basis = 0` for assigned positions, which is why the BigQuery chain was built. That was **not reproducible on 2026-07-30 or 2026-07-31** — all four assigned lots returned correct non-zero values. Since the whole design now rests on that field, the build must (a) confirm the behavior across a fresh assignment, and (b) guarantee the fail-closed path is exercised by test, so a regression to zero halts writing rather than writing unprotected.

### Phase 2 — One floor implementation

- Route `CallRoller`'s floor (`call_roller.py:127-132`) through `CostBasisResolver` and make its zero case **fail closed** — today it degrades to `min_strike = current_strike + 0.01`, which is no basis protection at all, on the one path that places orders without passing `execute_call_sale`. This satisfies the floor half of **FC-062**; routing `execute_roll` through the shared gate remains FC-062's.
- Reconcile the equality semantics: gates allow `strike == floor`, but the scanner's `assignment_above_cost_basis` flag uses strict `>`, so GOOGL's at-floor 370C was flagged `False` and sold anyway. Fix the flag to match the gate (at-floor is allowed and correct — see "At-floor writes" above), so it stops reading as a warning that gates nothing.
- The 90-day cliff and the Alpaca-fallback demotion are handled in Phase 1, since under this plan's definition they are floor-*correctness* defects rather than observability ones.

### Phase 3 — Regime protection on the live path (the original FC-065)

Port FC-029's drawdown pause and defer-on-bad-quote to the scanner path, reusing `CostBasisResolver` and the **existing event names** (`covered_call_drawdown_pause`, `covered_call_quote_missing`) so the backtest rejection taxonomy (`src/backtesting/engine/rejections.py:44`) and any dashboard consumer keep working.

Design decision: implement as a **scanner-side skip**, not a selection-side drop. The pause is a per-symbol regime judgment, not a per-contract one, and skipping at scan keeps the opportunity blob an accurate record of what was considered tradeable. (FC-038's drop-reason model is right for per-contract decisions; this is not one.)

**Honesty about the pause's marginal effect (trader review):** with a working floor and the [0.15, 0.25] band, deep-underwater symbols already yield nothing (NVDA, verified) — there the pause adds only legibility. The band where the *gate* changes behavior is roughly 5%-to-band-exhaustion, where it blocks **above-floor, cycle-net-positive, high-IV writes** — real foregone premium, not zero. The gate is kept because the operator's policy is "hold until recovery, then write," but the 0–5% band semantics and the threshold itself are **Open Question 3 — operator decision.** (The trader's alternative — pause as a derived decision-record *label* with no gate — delivers the legibility at zero premium cost and is the fallback if the operator wants floor-only gating.)

**Emission policy:** `covered_call_drawdown_pause` fires on **transitions only** (entered/exited pause); steady state lives in the Phase 4 decision record, which carries `paused` plus **pause duration in days**. Per-scan emission would fire ~6×/day indefinitely (NVDA has been underwater since June) — the same noise lesson `cost_basis_resolved_via_fallback` just taught.

**Accepted staleness window:** scanner-side skip means no execution-time pause re-check; a fast crash inside the ≤30-minute blob window can execute an above-floor write on a symbol that would now pause. The execute-time floor still holds, so the worst case is an above-floor write mid-crash — accepted, recorded.

### Phase 4 — Make the decision legible

- **Fix the zeroed telemetry.** `call_sale_executed` (`call_seller.py:436-438`) reads wheel-engine-only keys; use the same shape-tolerant accessor FC-050 introduced. This is small, and it is the reason FC-029's standing production-validation item is currently unsatisfiable.
- **Emit one decision record per held symbol per cycle** with a closed outcome enum: `sold | no_candidates{reason counts} | dropped{reason} | blocked{floor|unresolved|divergent} | paused{drawdown, duration_days} | not_eligible{<100 shares}`. FC-038's drop-reason enum already proves the pattern works.
- **This requires a `run_id`, and it reconciles with FC-044 rather than duplicating it (architect review).** `sold`/`dropped` are decided in `/run`, a separate stateless request ~15 minutes after `/scan`, and today **no identifier joins the two** (FC-044's survey; the blob is the only correlator). Fix: mint a `run_id` at scan time, store it in the opportunity blob, and thread it through `/run`. The decision table **adopts FC-044 Phase 1's `decision_events` design** (nearly field-for-field what this phase needs) — FC-044 Phase 1 is subsumed here; FC-044's Phase 2 grid UI remains its own FC reading this table.
- **Idempotency and liveness (architect review):** dedup key = `(run_id, symbol, stage)` — this codebase just produced 36× duplicated `wheel_cycles` rows from an unkeyed fire-and-forget writer, and Cloud Scheduler retries will do it again; and the table's fill rate is itself monitored (one row per held symbol per scan-hour expected; the FC-046 sink died silently for eight months because nothing watched it).
- **Make it durable.** Structured events currently live only in Cloud Logging's 30-day window because the BigQuery sink died 2025-11-22 (FC-046), so *a question about last month's decision is already unanswerable today*. The decision table via `analytics_writer` is the durable path; it does not inherit the sink's repeated-field schema collision.
- **Repoint the FC-030/FC-031 pause observability (architect review — breaks otherwise):** the dashboard pause card and the daily ≥7-trading-day pause alert infer pause state from the **OPASN strike** (`dashboard/backend/services/bigquery.py:1501-1509`); after Phases 1+3 the bot pauses against `avg_entry_price`, so near the threshold the alert and the bot would disagree — and under hold-until-recovery that alert is the *only* escalation control for idle capital. Both consumers move onto the pause events / decision records this plan emits.

## Risks & mitigations

- **Risk: Phase 1 lowers every floor by one put premium.** Mitigation: verified that no tradeable strike falls in any of the four gaps, so the qualifying strike set is unchanged; the acceptance test asserts that identity per symbol rather than asserting the floor number itself. Re-check if the universe gains underlyings whose strike increment is finer than a typical put premium.
- **Risk: the whole floor now rests on a single broker field.** Mitigation: fail closed on zero/missing (test-enforced), plus the BigQuery cross-check alerting when the Alpaca-vs-paid gap deviates from the expected put premium — which is how a corporate action, partial sale, or a regression to FC-029's reported `cost_basis = 0` behavior would surface.
- **Risk: porting the pause starves symbols that currently trade.** Mitigation: the pause fires at 5% underwater; today only NVDA (9.5%) and GOOGL (4.3%) are near it, and NVDA already yields zero candidates. Expected behavior change is ~zero contracts, ~one new event — verify in the first two cycles.
- **Risk: scope.** Four phases is still a lot. Mitigation: each is independently shippable and independently valuable; Phases 1–2 are the money path and can ship alone if the rest is deferred. (The backtest-repoint risk moved to FC-068 with the phase.)
