## Context

The dashboard frontend (5 pages, 1,210 LOC, audited 2026-05-04) is technically functional — every endpoint returns 200, the code follows reasonable React patterns, only one real field-name bug exists (WheelCycles dates). But the *product* is wrong: it was built without product input, surfaces raw data without curation, and tries to do too much. The user reports it as generally not useful for the actual decisions a wheel-strategy operator needs to make.

The data layer is no longer the constraint. FC-012 (shipped 2026-04-24) replaced runtime-logged BQ tables with Alpaca-sourced views (`trades_with_outcomes`, `equity_history_from_alpaca`, `wheel_cycles_from_activities`) and the data is clean, current, and queryable.

External research across r/thetagang resources, open-source wheel trackers (Wheeler, agamotto, premium-tracker, OptionWheelTracker), and critique pieces (Early Retirement Now, QuantWheel) produced strong consensus on what a credible wheel dashboard surfaces and what's vanity. This rebuild bakes those findings in from the start.

## Goals

- 3 focused pages organized by **underlying symbol as primary lens**, not by data type.
- **XIRR-on-NLV** as the headline performance number.
- Premium collected **always shown alongside unrealized P&L** on assigned shares — never alone.
- **Vs-buy-and-hold-per-symbol** as a first-class column (the metric that answers "is the wheel adding value here").
- **Bot Health** page that surfaces gate hit counts, errors, scan cadence — for operational debugging the user explicitly asked for.
- Backend essentially unchanged — only new SQL views, no new ingest jobs.
- Old frontend archived to `dashboard/frontend.archive/` for future reference, **not deployed**.

## Non-goals

- Counterfactual "should I have rolled?" or "was there a better strike?" analysis. Requires option-chain snapshots at decision time. **Deferred to FC-017** as a separate prerequisite.
- Mobile-optimized UX. Desktop-first.
- Alerting / notifications.
- Multi-user, auth changes, or any change to the existing service-to-service auth.
- Tech stack changes. React/Vite/Tailwind/FastAPI stays. No SSR, no Next.js, no rewrite of the data layer.
- Migration of the bot-side log sink (`options_wheel_logs` dataset). Out of scope per FC-012's existing decisions.
- "Win rate" as a headline metric. Research consensus: vanity unless paired with avg-win/avg-loss ratio. Optionally shown in a small sidebar with the ratio next to it; never the headline.

## Proposed approach

Three pages. Each page section below specifies (a) what's on it, (b) which API endpoints it consumes, (c) which BQ views/methods power those endpoints, and (d) any new data layer pieces needed.

### Page 1 — Overview (`/v2/overview`)

Single page. Combines overall portfolio performance with a per-symbol scorecard. The "what's the state of my strategy?" page.

**Top section — Portfolio summary**

- **Headline KPIs (4 tiles, single row):** NLV (current), XIRR-on-NLV (trailing 12mo or since-inception, with a small selector), Cumulative net P&L (realized premium − unrealized P&L on assigned shares), Days running.
- **Equity curve** — line chart of NLV over time. Source: `equity_history_from_alpaca`.
- **Monthly stacked premium bars** — by month, segmented into put premium / call premium / realized stock P&L (from called-away assignments). Source: aggregation over `trades_with_outcomes`.
- **Stress row (single line):** "If all open CSPs were assigned at current price, mark-to-market = $X." Computed from open positions × strike vs. current price.
- **Account snapshot (small):** Cash, BP utilization, deployed collateral.

**Middle section — Per-symbol scorecard**

Sortable matrix table. One row per underlying that has any trading history. Columns:

| Column | Source |
|---|---|
| Symbol | underlying |
| Position state | derived: cash / short put / long stock / long stock + short call |
| Cycles completed | count from `wheel_cycles_from_activities` |
| Trades (open + close events) | count from `trades_with_outcomes` |
| Total premium collected | sum of `premium_total` |
| Current ACB (if holding stock) | new view: `acb_per_symbol_current` |
| Current price | live from `/v2/positions` or last bar |
| Realized P&L | sum of `realized_pnl` for closed events |
| Unrealized P&L on shares | (current_price − ACB) × shares |
| **vs. buy-and-hold (delta $)** | new view: `vs_buy_and_hold_per_symbol` |
| **vs. buy-and-hold (delta %)** | derived |

Default sort: total premium descending. Click any row → Page 2 (drilldown for that symbol).

**Bottom section — Action panel**

Compact list of open positions needing attention. Filters applied: `DTE ≤ 7` OR `% to strike < 5%` OR `earnings before expiry` OR `≥50% of max profit captured`.

Columns: symbol, type (put/call), strike, DTE, current premium, % of max profit, distance-to-strike, manage-flag badges. Source: `/api/live/positions` + `/api/history/trades` (recent opens).

### Page 2 — Per-symbol drilldown (`/v2/symbol/:underlying`)

The wheel-centric heart of the dashboard. Everything for ONE underlying, in one place.

**Top — Symbol header**

Symbol, current price, position state, total premium collected, cycles completed, vs-buy-and-hold delta. One-line summary.

**Section A — ACB walk chart (the wheel community's most-discussed visualization)**

Stepped line chart showing adjusted cost basis over time. Each step annotated with the event that caused it: put premium received, assignment (large step *up* to strike), call premium received, called-away (terminates the campaign).

Formula: `ACB = (share_cost − net_premiums) / shares`, where `share_cost` is the strike at which shares were assigned. Pre-assignment, the chart shows premium accumulation against zero share count (dashed line).

Source: new view `acb_timeline_per_symbol` joining `trades_with_outcomes` events into a stepped sequence.

**Section B — Cycle table**

Every wheel cycle on this symbol. Columns: put_date, put_strike, put_premium, assignment_date, call_date, call_strike, call_premium, called_away_date, total_premium, cycle_duration, annualized_return, capital_gain. Source: `wheel_cycles_from_activities` filtered to this symbol.

**Section C — Decision quality histogram**

Distribution of "% of max profit captured at close" across all closed trades on this symbol. Bins: 0-25, 25-50, 50-75, 75-100. Helps identify systematic over/under-trading. Source: derived from `trades_with_outcomes` (close fill price vs original premium).

**Section D — Trade log**

Chronological list of every event (sell put, buy_to_close, OPASN, OPEXP, sell call, called away). One row per event. Source: `trades_from_activities` filtered to this symbol.

**Section E — Phase timing**

Bar showing days spent in each phase (cash-waiting / short put / long stock / long stock + short call). Diagnoses capital drag.

**Section F — vs. buy-and-hold for this symbol**

Two lines on one chart: actual wheel-strategy account contribution from this symbol vs. hypothetical buy-and-hold of the same dollar amount of shares from the first cycle's start. Source: new view `vs_buy_and_hold_per_symbol`. Requires historical EOD bars.

### Page 3 — Bot Health (`/v2/bot-health`)

Operational debugging. The user explicitly asked for this view.

- **Gate hit counts:** filtering pipeline stages 1-9 with hit counts over rolling 7d / 30d. Heatmap or stacked bars by date. Source: `/api/history/filtering` (uses `scans` table).
- **Recent errors:** last 50 errors with frequency rollup by `error_type` and `component`. Source: `/api/history/errors`.
- **Scan cadence:** last-N successful scans, last-N successful runs, last-N successful monitors. Anomaly flags: zero-opportunity days, unusual failure spikes. Source: `/api/history/daily-summary`.
- **Ingest health (FC-012):** last successful run of `/ingest-activities` and `/ingest-portfolio-history`. Stale-data warning if either is >24h old. Source: query `MAX(ingested_at)` from the FC-012 tables.

## Data layer additions

New file: `docs/bigquery/fc018_views.sql`. Views:

1. **`per_symbol_scorecard`** — one row per underlying with all the columns the Overview matrix needs. Aggregates `trades_with_outcomes` by `underlying`.
2. **`acb_timeline_per_symbol`** — one row per premium/assignment event, with running ACB. Powers Page 2's ACB chart.
3. **`acb_per_symbol_current`** — single-row-per-symbol projection from the timeline view returning the *latest* ACB. Used by Overview matrix.

Vs-buy-and-hold requires historical stock bars Alpaca's `/v2/stocks/bars` provides:

4. **New BQ table `stock_history_from_alpaca`** — daily bars (date, symbol, close). Populated by a new ingest endpoint `/ingest-stock-history` triggered daily by Cloud Scheduler. Backfill on first run for the universe of traded symbols. Append-only, idempotent by `(date, symbol)`.
5. **`vs_buy_and_hold_per_symbol`** — view joining per-symbol wheel realized+unrealized P&L against `stock_history_from_alpaca` for synthetic buy-and-hold of same dollar amount from cycle-start.

New backend BigQueryService methods (extending `dashboard/backend/services/bigquery.py`):

- `get_per_symbol_scorecard(days)` → Page 1 matrix.
- `get_acb_timeline(symbol, days)` → Page 2 Section A.
- `get_decision_quality(symbol, days)` → Page 2 Section C.
- `get_phase_timing(symbol, days)` → Page 2 Section E.
- `get_vs_buy_and_hold(symbol, days)` → Page 2 Section F + Overview matrix column.
- `get_ingest_health()` → Page 3 ingest-health card.

New routers:

- `POST /api/admin/ingest-stock-history` (or extend existing scheduler infra) for the new bars ingest.
- New GET endpoints for the methods above. Path convention: `/api/v2/...` to match the frontend `/v2/...` strangler routes.

## Frontend rebuild

### Migration sequence (strangler)

1. **Archive old**: move `dashboard/frontend/` → `dashboard/frontend.archive/`. Update `cloudbuild.yaml` and `dashboard/Dockerfile` to skip the archive directory in builds.
2. **Skeleton**: create new `dashboard/frontend/` with same Vite/React/Tailwind setup. Copy over `Layout`, `ErrorBoundary`, `ErrorState`, `LoadingState`, `useApi` (or replace with React Query — decision in plan execution).
3. **Page 1 (Overview)**: build at `/v2/overview`. Ship + visual review.
4. **Page 2 (Symbol drilldown)**: build at `/v2/symbol/:underlying`. Ship + visual review. Wire Overview row clicks to navigate.
5. **Page 3 (Bot Health)**: build at `/v2/bot-health`. Ship + visual review.
6. **Tests**: unit tests for each page component + the data hooks. Component tests for the per-symbol matrix sort/filter behavior.
7. **Cutover**: in `App.tsx`, redirect `/`, `/performance`, `/positions`, `/trades`, `/wheel-cycles` to the relevant `/v2/...` paths. Old archived code is not deployed; the redirects only handle bookmarks.
8. **Final cleanup PR (≥3 days after cutover stable)**: drop `/v2/` prefix, restore canonical paths. Delete `dashboard/frontend.archive/` if user is comfortable.

### Charting library

Old frontend uses no charting library based on audit. New stack candidate: **Recharts** (React-native, composable, MIT). Decision finalized in plan execution; first chart written in Recharts is the validation point.

### Data fetching

Audit noted a custom `useApi` hook. For the rebuild, evaluate **TanStack Query (React Query)** — gives us request deduping, background refresh, and cache invalidation for free. Decision in plan execution. If `useApi` proves sufficient, keep it.

## Risks & mitigations

- **Risk: scope creep.** Hard 3-page limit in this plan. Any chart/feature that doesn't fit one of those pages is out of scope or filed as a follow-up FC.
   - *Mitigation:* explicit "this is what NOT to build" non-goals section. Plan PRs reject feature additions outside scope.

- **Risk: vs-buy-and-hold computation is more work than expected.** It needs historical bars for ~14 symbols × 6+ months and a synthetic-portfolio comparison. The bars ingest is novel for this codebase.
   - *Mitigation:* time-box the bars ingest to a focused half-day. If blocked, ship Page 1 without the vs-B&H column and add it as a follow-up. The other Overview features stand alone.

- **Risk: Alpaca rate limits on bar history.** Backfill across the universe could be ~14 symbols × 180 days × N requests.
   - *Mitigation:* Alpaca's bars endpoint supports date-range queries; one call per symbol covers the whole window. ~14 calls total for backfill, well under rate limits. Daily incremental thereafter is 14 calls/day.

- **Risk: visual regression / "I miss feature X from the old dashboard."** Strangler migration mitigates this by keeping old code archived (just not deployed). User can pull it back if a critical feature was lost.
   - *Mitigation:* don't delete `dashboard/frontend.archive/` until ≥3 days after final cutover and explicit user OK.

- **Risk: chart library learning curve.** Recharts is mainstream but the team has no install base.
   - *Mitigation:* first chart (equity curve) is the validation. If Recharts feels wrong, switch to Chart.js or Apache ECharts before sinking 5 charts in.

- **Risk: backend changes break FC-012 dashboard during the build window.** New view definitions or method additions could conflict with existing reads.
   - *Mitigation:* new views use new names (`per_symbol_scorecard`, etc.), don't modify FC-012's `trades_with_outcomes` etc. New methods are additions to `BigQueryService`; existing methods untouched.

- **Risk: tests skipped under deadline pressure.** The current frontend has zero tests; that legacy will tempt skipping tests on the rebuild too.
   - *Mitigation:* tests written per page, not at the end. Each page's PR includes its own tests. No-tests PRs blocked at review.

## Rollout

Per-page rollout, with one small PR per page:

1. **PR A — Archive + skeleton** (small): move old frontend to archive, update build excludes, scaffold new frontend with shared components.
2. **PR B — Backend additions** (medium): new SQL views, new BigQueryService methods, new `/api/v2/...` endpoints, new `stock_history_ingestor.py` + endpoint + scheduler doc. Backend can ship before frontend uses it.
3. **PR C — Page 1 (Overview)** (medium): components, page, route, tests. User reviews live.
4. **PR D — Page 2 (Symbol drilldown)** (large): more components, ACB chart is the heaviest piece.
5. **PR E — Page 3 (Bot Health)** (small): straightforward views over existing data.
6. **PR F — Cutover** (small): redirect old paths to `/v2/...`. No code changes to pages.
7. **PR G — Final cleanup** (small, ≥3 days post-cutover): drop `/v2/` prefix, restore canonical paths, optionally delete `dashboard/frontend.archive/`.

Rollback at any stage: revert the PR. Old archived frontend not in build path; restoring it is a one-line `cloudbuild.yaml` change + reversal of the archive move.

## Open questions

Decided in plan execution, not blocking the FC:

- **Charting library** — Recharts default. Alternatives: Chart.js, Apache ECharts, Visx. First chart is the validation point.
- **Data fetching** — keep `useApi` or migrate to TanStack Query. Lean Query if we hit complex caching needs; otherwise `useApi`.
- **Stock-history caching** — new BQ table `stock_history_from_alpaca` (proposed in this plan) vs. caching in dashboard backend memory. Default: BQ table for shareability + persistence.
- **Per-symbol matrix sort/filter** — server-side or client-side. Default: client-side (~14 rows; trivial).
- **Date range selector — global or per-page?** Default: global selector on Overview header (30d / 90d / YTD / 1Y / All); per-chart only when the data demands it (drilldown ACB walks all-time by default).
- **Decision quality on Page 2 — should it pivot to time series?** I.e., "% of max profit captured at close" *over time* rather than just a histogram. Adds value for spotting drift; defer to Page 2 build for visual call.
- **Page 1 action panel — fold into Overview or split into a 4th "Today" page?** Current proposal folds it. If the action panel grows beyond ~5 rows of detail in practice, split into a separate page in a follow-up FC.
