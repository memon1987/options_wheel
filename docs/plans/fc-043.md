# Plan: Fix `AlpacaClient.get_orders` — the status filter has never worked

**FC entry:** `docs/FUTURE_CONSIDERATIONS.md` FC-043
**Plan file:** `docs/plans/fc-043.md`
**Status:** Published
**Size:** S (one wrapper function; live-behavior change)
**Author:** zeshan + Claude
**Last updated:** 2026-07-24

## Context

`AlpacaClient.get_orders(status=...)` (`src/api/alpaca_client.py:632`) has two
independent defects, and between them the `status` argument has **never
selected the orders the caller asked for** since the wrapper was written:

1. **It never passes a request filter.** It calls
   `self.trading_client.get_orders()` with no `GetOrdersRequest`, so Alpaca's
   REST default (`status=open`) always applies — closed orders are never even
   fetched, regardless of the `status` argument.
2. **It value-filters against the wrong vocabulary.** It then keeps orders where
   `order.status.value.lower() == status.lower()`. But callers pass Alpaca's
   *query* tokens (`'open'`), which are **not** order-status *values*. An open
   order's `status.value` is `new` / `accepted` / `pending_new`, never `'open'`
   (verified: `'open' in [s.value for s in OrderStatus]` is `False`). So the
   comparison can never match.

### Who this breaks (all three live callers)

| Caller | Arg | Intent | Actual result today |
|---|---|---|---|
| `wheel_engine.py:496` Stage-6 duplicate guard, Check 2 | `'open'` | block new entry if an unfilled order for this underlying exists | `[]` **always** — the guard's API check is dead |
| `wheel_engine.py:497` Stage-6 guard | `'pending_new'` | same | effectively never matches (transient bucket, and only the open set is fetched) |
| `portfolio_tracker.py:315` | `'filled'` | last 10 filled orders for reporting | `[]` **always** — `filled` lives in the CLOSED bucket, which is never fetched |

**Why the duplicate guard matters most.** Check 2 is the **only** duplicate
backstop that survives a Cloud Run cold start. Check 1 (`_pending_underlyings`)
is in-process and resets to empty on every new instance; Check 3 catches only
*filled* positions, not orders still resting at the broker. Check 2 was written
as the "race condition fix" (its own comment) to close exactly the FC-009
window: order placed → instance scales to zero → new instance re-evaluates with
an empty local set → **places a second order for the same underlying**. Because
Check 2 returns `[]` unconditionally, that window is currently unguarded. FC-009
is a *confirmed* duplicate-order bug; this is a direct contributor.

### Verified against live Alpaca (2026-07-24, paper)

- `OrderStatus` values do **not** include `open` or `closed` — those are
  `QueryOrderStatus` (query) tokens only.
- `GetOrdersRequest(status=CLOSED)` returns `{filled, expired}`;
  `GetOrdersRequest(status=OPEN)` returns the unfilled set. The wrapper fetches
  neither correctly.
- Current wrapper: `get_orders('open')`, `get_orders('pending_new')`,
  `get_orders('filled')`, `get_orders(None)` **all return 0** against an account
  with 500 closed orders.

## Goal

`get_orders(status=...)` returns the orders the caller asked for, fixing all
three callers at the root, with no change to the dict shape it already returns.

## Non-goals

- **Not** touching the FC-035 poll path (`wheel_engine.py:~716`); that is PR #47,
  held for a separate decision, and it calls `trading_client` directly. This fix
  does not overlap it. If #47 later merges, the wrapper being correct is an
  enabling cleanup, not a conflict.
- **Not** changing the guard's fail-open `except` (Check 2 swallows API errors
  and proceeds). That is a separate risk decision; noted for a reviewer, left
  as-is so this change is scoped to the filter defect.
- No change to `_pending_underlyings` (Check 1) or the cold-start persistence
  question — FC-009's in-memory-dedup root cause is broader and stays in FC-009.

## The fix

Rewrite `get_orders` to map the `status` string to the correct
`QueryOrderStatus` bucket, fetch with an explicit `GetOrdersRequest`, then
value-filter only when the caller named a specific status value:

- `None` → `QueryOrderStatus.ALL`, no value filter
- `'open'` → `QueryOrderStatus.OPEN`, no value filter
- `'closed'` → `QueryOrderStatus.CLOSED`, no value filter
- a specific status value (`'filled'`, `'expired'`, `'pending_new'`, `'canceled'`,
  …) → fetch the bucket it lives in (OPEN for the unfilled/pending values,
  CLOSED otherwise), then keep rows whose `status.value` matches.

Pass an explicit `limit` (500) so ALL/CLOSED are not silently truncated at
Alpaca's default of 50. Preserve the returned dict keys exactly.

### Behavior change and its risk

`get_orders('open')` flips from "always `[]`" to "the real open set", so the
Stage-6 guard begins blocking a new entry when an unfilled order for the same
underlying is resting. Intended. Only over-blocks if an order lingers open — but
the bot places **DAY** marketable orders on ≤7-DTE options, which resolve
same-session, so a stale open order is not a realistic standing state. Reviewers
should probe this.

## Tests

- Unit: mock `trading_client.get_orders`; assert the wrapper passes
  `GetOrdersRequest(status=OPEN)` for `'open'`, `CLOSED` for `'filled'`, `ALL`
  for `None`, and that value-filtering keeps/drops correctly. A regression test
  that fails on the current code (asserts `'open'` returns a resting order).
- Integration-ish: a `WheelEngine._check_existing_option_position` test proving
  Check 2 returns `True` when an open order for the underlying exists (it
  currently returns `False` and falls through).
- Full suite green (596+).
