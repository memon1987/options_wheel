## Rev 1 (superseded 2026-08-01)

Rev 1 (2026-04-29) responded to the GOOG incident by wiring the earnings gate into
`PutSeller.find_put_opportunity` and `CallSeller.evaluate_covered_call_opportunity`,
injected from `WheelEngine`. **Every one of those wiring targets is deleted by FC-068**
(`docs/plans/fc-068.md` §1–3): the engine builds no sellers, and both seller-side
opportunity producers are gone. Production trades via `/scan` → `OptionsScanner` →
GCS blob → `/run` → `ExecutionEngine` → the sellers' `execute_*` methods, and the
backtest now replays that exact pipeline.

**What survives from rev 1:** the `EarningsCalendarService` service-layer decisions
(Finnhub, in-memory cache, failure cache, `get_earnings_proximity` enrichment); the
fail-closed instinct (operator-reconfirmed at FC-069 sign-off); activating the
`earnings.blackout_days` knob; the test-matrix shape (gate fires / allows / blocks on
failure / no-op when disabled); the `docs/gates.md` deliverable.

**What rev 2 corrects in rev 1, beyond the deleted wiring targets:**

1. **Rev 1's fail-closed spec (§3) was buggy as written.** It flipped
   `is_earnings_within_n_days`'s error paths to return `True` — but that method's
   `days_until is None` branch conflates two different states: *"Finnhub fetch
   failed"* (`_fetch_earnings` returned `None`) and *"no earnings scheduled in the
   next 90 days"* (a successful fetch cached as `{"date": None}`). Flipping the
   `None` branch would have blocked every known-clear symbol — an account-wide
   brick on normal days. Rev 2 introduces a tri-state method instead (§Approach 2).
2. **Deleting `earnings_avoidance_days` moved to FC-069's sweep** (item 4 decision
   line, binding). This plan does not touch it.
3. **Rev 1's fail-closed flip changed the roller's behavior.** Operator decision
   (FC-069): the roller keeps its existing gate unchanged. Rev 2 confines the new
   semantics to the new gate; `is_earnings_within_n_days` is untouched.

## Context

**Two incidents on record, same root cause: no earnings gate has ever existed on any
path that trades.**

- A GOOG cash-secured put executed **2026-04-28**, the day before Google's earnings.
- An AAPL covered call was sold the week of **2026-07-27**, days before Apple's
  earnings.

Verified against the post-FC-068 tree (`origin/fc-068/engine-path-deletion`, tip
`c72127a` — the base this plan builds on): zero earnings references in
`src/data/options_scanner.py`, `src/strategy/put_seller.py`,
`src/strategy/call_seller.py`, `src/strategy/execution_engine.py`. The only earnings
consumers are the Friday roller (`CallRoller.should_roll` — the `earnings_blackout`
gate, structurally no-op'd by the quote-key bug, FC-066) and the backtest's roller
seam (`HistoricalEarningsCalendar`, threaded through `WheelEngine` in
`simulator.py`). The `earnings.*` knobs (`settings.yaml`: `enabled: true`,
`cache_ttl_hours: 24`, `blackout_days: 2`, `lookahead_days: 90`) read as live and
gate nothing that opens a position.

**Operator decisions (FC-069 item 4 sign-off, 2026-08-01 — binding, not relitigated
here):**

- The earnings gate is a key part of the gating strategy. **REVIVE.**
- Gate **both** put opens and call opens. The roller keeps its existing gate.
- **Live and backtest coverage.** Post-FC-068 the simulator replays the scanner
  pipeline, so a scanner-layer gate applies in replays via the
  `HistoricalEarningsCalendar` seam — threaded explicitly (the FC-068-created
  obligation this plan discharges).
- Finnhub service, `FINNHUB_API_KEY`, and the `earnings.*` knobs stay.
- The dead `risk.gap_risk_controls.earnings_avoidance_days` knob dies in FC-069's
  sweep, not here.

**New findings from this re-plan (verified against `c72127a`):**

- **The 24h earnings cache is fictional at request scope.** `EarningsCalendarService`
  keeps `_cache` on the instance; `/scan` constructs a fresh `OptionsScanner` per
  request (`cloud_run_server.py`, `trigger_scan`), so a scanner-owned service would
  re-fetch every symbol on every scan — ~14 Finnhub calls × ~13 scans/day. Same
  defect class as `_entry_times` (sellers per-request, FC-069 item 6). §Approach 4
  moves the cache to module scope, making `earnings.cache_ttl_hours` real on the
  scan path for the first time.
- **The FC-069 card's Finnhub-volume aside is backwards.** Card 4(c)(i) says
  scanner-side placement "spares Finnhub calls for symbols that produce no
  candidates" — in fact selection-side would need *fewer* lookups (only symbols that
  produced candidates). The placement decision below does not rest on call volume
  either way; with the shared cache the difference is ≤14 cached lookups/day.

## Goals

- One earnings gate, at the scanner, covering **both** legs: a symbol within the
  blackout window produces no put opportunities and no call opportunities.
- The same gate object works in production (`EarningsCalendarService`, Finnhub) and
  in replays (`HistoricalEarningsCalendar`, committed point-in-time table) through
  one injected seam.
- **Fail closed on unknown**: when the calendar cannot answer (Finnhub outage,
  missing key), the symbol is skipped — loudly, with an event that distinguishes
  "blocked by real earnings" from "blocked because we could not tell".
- Every skip is legible: structured events on both legs, a P4 decision-record row on
  the call leg, replay-tally mappings on both legs.
- The blackout window **value** is chosen by the operator on data, not inherited:
  the exposure audit (§Approach 6) runs before wiring begins.
- `docs/gates.md` ships: the live-path gate inventory FC-069 items 3/14 plan to
  point at.

## Non-goals

- Deleting `earnings_avoidance_days` (FC-069 sweep, binding).
- Unifying `rolling.earnings_blackout_days` with `earnings.blackout_days`, or any
  change to the roller's gate (§Design decision 5: FC-066's turf, item 13 HOLD).
- Per-symbol blackout windows (universe of 14; single global knob, as rev 1 decided).
- Closing existing positions ahead of earnings (conflicts with FC-010
  assignment-tolerance; the wheel takes assignment).
- Extending the P4 `decision_events` table to the put leg. That table is by design
  the per-held-symbol *covered-call* decision record; put-side legibility here is
  events + tally + the committed audit script (§Approach 6). A put-side decision
  table is its own FC if ever wanted.
- A span-based gate ("block when the candidate's expiry crosses earnings") —
  considered and deferred, see Design decision 3.
- New alerting channels (Design decision 6) or a card-16 detective check (FC-069's
  turf).
- `/monitor` (closes reduce risk; never gated) and `/run` (gate is upstream, §DD-1).

## Design decisions

### DD-1 — Placement: scanner-side symbol gate (both legs), not selection-side, not both

**Chosen:** a symbol-level gate inside `OptionsScanner`, before opportunity
construction on each leg.

**Rejected — selection-side drop (`select_batch`, new `DROP_EARNINGS_BLACKOUT`):**

- `/run` has no earnings data and no natural place to get it: either
  `ExecutionEngine` grows its own Finnhub surface (a second copy of the outage
  problem, in the process that places orders), or the scan stamps proximity onto
  each opportunity and selection reads it — which is scan-time evaluation wearing a
  selection costume, plus blob plumbing.
- `DROP_REASONS` is FC-038's model for **batch-resource contention** — shares,
  buying power, duplicate-underlying — evaluated against *this batch*. Earnings is
  a symbol-level *policy* fact known before any chain is fetched. Wedging it into
  the drop model misfiles it.
- Selection-side wastes the scan: chains fetched, opportunities built and ranked
  for a symbol that cannot trade, plus (call leg) a BigQuery cost-basis cross-check
  spent on it.
- Observability is not better there: the call leg's drop would reach decision
  records via `/run`, but the scan-side gate reaches them too (§DD-4), and the put
  leg has no decision-record machinery on either side.

**Rejected — gate at both:** no incremental protection. `blackout_days` is a
days-granular predicate; between `/scan` and `/run` sit ≤30 minutes
(`opportunity_max_age_minutes`), inside market hours, never crossing midnight — the
predicate cannot change value in that window. Cost: a second Finnhub dependency
surface and a second failure-semantics decision, for nothing.

**Finnhub volume / latency, analyzed (the FC-069 card asked):** the gate consults
the calendar once per put-side suitable stock (≤14) and once per call-side held
symbol (≤7, overlapping) — with the shared module cache (§Approach 4), **≤14 unique
fetches per 24h per instance**, each ~150–400ms. Worst case (cold cache, first scan
of the day): +2–6s on the ~18.5s `/scan` baseline. Subsequent scans: cache hits,
~0ms. Finnhub free-tier limit is 60 calls/min; 14 sequential calls are well inside
it. Selection-side would fetch fewer symbols but the difference is noise once the
cache is request-surviving.

**The NVDA-silent-exclusion lesson is honored, not waived:** a scanner skip here is
*never* silent — call leg writes a decision-record row (§DD-4), both legs emit
structured events, both events are tally-mapped for replays (§Approach 5).

### DD-2 — Failure semantics: fail closed on unknown, via a new tri-state method

**Chosen: fail-closed.** When the calendar cannot answer for a symbol, that symbol
is skipped for this scan, on both legs, with a distinct "unknown" event.

The three options, weighed honestly:

- **Fail-closed** (chosen). A Finnhub outage at scan time means **no opens
  account-wide that day** — a bigger blast radius than rev 1's per-seller world,
  stated plainly. But the blast radius is *bounded and cheap*: one day of foregone
  opens on a strategy selling 7-DTE premium (order-of-magnitude: a few hundred
  dollars of premium deferred, not lost — the next scan retries within the hour
  after the 1h failure-cache expires). Existing positions, closes, and `/monitor`
  are untouched. It is consistent with the floor's discipline (FC-065: unresolved
  basis = no trade) and with the operator's reconfirmed fail-closed instinct.
- **Fail-open-with-alert** (rejected): trades through outages ungated — the gate is
  silently absent exactly when its input is unverifiable. This codebase's signature
  disease is controls that read as live and fail open (`STATE_STORAGE_BUCKET`, the
  min-hold gate, the pre-FC-065 floor); FC-069 item 8's standing note exists
  because of it. An alert does not stop the trade.
- **Fail-closed-with-stale-cache-grace** (rejected): serve last-known-good beyond
  TTL during outages. Sounds like a middle path; in practice the benefit is mostly
  illusory — the cache is in-process, Cloud Run instances recycle daily, and a
  morning outage meets a cold cache with nothing to be graceful with. Complexity
  without coverage.

**Mechanism — do not flip the existing method.** `is_earnings_within_n_days` stays
exactly as-is (the roller's gate, operator-decided unchanged; and its `None` branch
conflates "clear" with "unknown", rev 1's bug). New method on both calendar classes:

```
earnings_within(symbol, n_days) -> Optional[bool]
    True   — next earnings date within the window (block)
    False  — fetch succeeded, no earnings within the window (allow)
    None   — could not determine (fetch failed / no client / no key) → gate blocks
```

**Enabled-but-unusable is loud, not silent.** `earnings.enabled: true` with no
`FINNHUB_API_KEY` (the `--set-env-vars` wipe gotcha is a live deploy hazard) or a
failed finnhub import → `earnings_within` returns `None` → every symbol blocked,
every scan emits `*_skipped_earnings_unknown`, and service construction logs an
error event. That is the correct posture per FC-069 item 8's standing note: a
configured-but-unresolvable dependency must fail loudly, never silently no-op.
`earnings.enabled: false` disables the gate entirely (the atomic rollback lever) —
*disabled* and *broken* are different states with different behavior, by design.

I judge this decided, not a blocking operator question: the operator confirmed the
fail-closed instinct survives (FC-069 card 4), and the blast radius is bounded as
above. The account-wide-outage consequence is restated in §Risks so sign-off sees it.

### DD-3 — Blackout window: predicate pinned; value is a data-informed operator call (pre-build gate)

**Predicate, pinned exactly:** block symbol S when
`0 <= (next_earnings_date(S) − today) <= N` in **calendar days**, where `today` is
`date.today()` live and `clock.now().date()` in replays. Pre-earnings only:

- **Day-of (0) is blocked** — most earnings in this universe are AMC; day-of selling
  is the maximum-exposure trade.
- **Post-earnings is not covered.** The service only looks forward
  (`_from=today`), so a symbol that reported yesterday resolves to next quarter.
  This is deliberate, not an accident of the API: the day after earnings is
  IV-crush territory — elevated premium already collapsing, gap risk realized —
  and blocking it would cost the wheel some of its best entries.
- **Calendar days, not trading days** (rejected alternative): trading-day semantics
  give uniform protection across weekdays but add a market-calendar dependency to
  the gate. With calendar days, a Monday AMC reporter under N=2 is "blocked"
  Sat/Sun/Mon — effectively one trading day of protection — while a Wednesday
  reporter gets two. Stated and accepted; if the operator wants uniform trading-day
  protection, that is a knob-semantics change on top of this gate, not a different
  gate.

**Value: `blackout_days: 2` was never tuned, and ratifying it blind is exactly what
FC-069 exists to end.** The exposure audit (§Approach 6) is a **pre-build gate**: it
runs before any wiring is written (it is currently blocked on expired gcloud auth —
first build step is re-auth), and its output goes to the operator with the window
decision. Default stands at 2 absent contrary evidence.

**Considered and deferred — the span predicate.** For a 7-DTE seller, days-based
blackout under-covers: a put sold 5 days before earnings with 7 DTE *holds through*
the event, ungated at N=2. The arguably-correct risk predicate is "block when the
candidate's expiration ≥ the next earnings date" — but it is opportunity-level
(needs the candidate's expiry), which changes the gate's placement from a per-symbol
skip to a per-candidate filter and its observability shape with it. The audit
reports exposure counts under **both** predicates so the operator can see whether
spanning exposures dominate; if they do, span-gating is a follow-up FC, not a
mid-build swerve. This is the honest way to carry the question without unflagged
ambiguity.

### DD-4 — Decision-record integration: two new reasons under `blocked`, schema untouched

- `REASON_EARNINGS_BLACKOUT = "earnings_blackout"` and
  `REASON_EARNINGS_UNKNOWN = "earnings_unknown"`, both added to
  `ALLOWED_REASONS[OUTCOME_BLOCKED]` in `src/data/decision_record.py`. Two reasons,
  not one: a row that says "earnings blackout" when Finnhub was down is a mislabel,
  and the closed vocabulary exists precisely so rows cannot misfile
  (`UnknownDecisionOutcome`'s reason for being).
- **No new outcome** — `blocked` already means "a policy gate terminated this
  symbol at scan"; the floor reasons prove the shape.
- **No schema change.** `decision_events` columns are untouched; earnings detail
  (`next_earnings_date`, `days_until`, `earnings_hour`) rides the structured log
  event, not the record row. The `_LABEL_FIELDS` labels
  (`shares`/`current_price`/`uncovered_days`) ride as usual;
  `cost_basis_per_share`/`underwater` are absent on earnings-blocked rows because
  the gate fires *before* basis resolution (§Approach 3) — nullable columns, same
  as several existing row shapes.
- Dedup key `(run_id, symbol, stage)` and the `sold`-wins ordering are unaffected.
- **Closed-enum tests:** `tests/test_decision_record.py`'s enum class gains
  `validate_outcome(OUTCOME_BLOCKED, REASON_EARNINGS_BLACKOUT/…UNKNOWN)` acceptance
  cases; the cross-pairing rejection test (`dropped` × floor reason, etc.) is
  extended to assert `validate_outcome(OUTCOME_DROPPED, REASON_EARNINGS_BLACKOUT)`
  still raises. No existing assertion weakens.
- **Cascading-impact check (docs/CLAUDE.md rule):** the dashboard reader
  (`dashboard/backend/services/bigquery.py::_decision_snapshot_query`) selects
  `reason` as a free string — additive-safe. Build step: check the
  `UncoveredPositionsCard` frontend reason-label mapping; if it maps reasons to
  display strings, add the two new labels in the same PR.

### DD-5 — Roller consistency: two knobs stay, unification is FC-066's

`rolling.earnings_blackout_days` (roller) and `earnings.blackout_days` (this gate)
remain separate knobs — both currently 2. Unifying now would reach into the
roller's config surface while FC-069 item 13 holds all `rolling.*` keys for
FC-066's revival decision; this plan honors that HOLD. FC-066's pre-revival
checklist is the right home for the unification question (and for adopting
`earnings_within` on the roll path if FC-066 wants fail-closed there too). Stated
here so the asymmetry is a recorded decision, not an oversight.

### DD-6 — Alerting: nothing new

A blackout skip is the gate working — normal operation, visible in decision records
and events, not an incident. A Finnhub outage already emits `earnings_fetch_failed`
error events (`recoverable=True`) which flow through the existing FC-030
error-event alerting baseline; the new `*_skipped_earnings_unknown` events make the
blocked-because-unknown state grep-able in Cloud Logging. If outage-blocking turns
out to be frequent, an alert policy is a config change on evidence — not built
speculatively here.

## Proposed approach

All file/line references against `origin/fc-068/engine-path-deletion` @ `c72127a`.
Symbol names are the contract; lines will drift at rebase.

### 1. `EarningsCalendarService` — tri-state method + module-scope cache

`src/api/earnings_calendar.py`:

- **Add `earnings_within(self, symbol: str, n_days: int) -> Optional[bool]`:**
  - `self._enabled` false → `None` is *wrong* here — the scanner never consults the
    calendar when the gate is disabled (§3), so this method may assume enabled.
    Defensively: `not self._client` → `None` (unusable ⇒ unknown ⇒ caller blocks).
  - Cached/fetched entry with `date is None` (successful fetch, nothing in the 90d
    lookahead) → `False` (known clear).
  - Entry with a date → `0 <= (date - date.today()).days <= n_days`.
  - `_fetch_earnings` returned `None` (failure, incl. failure-cache window) →
    `None` (unknown).
- **Constructor loudness:** when `config.earnings_enabled` is true and the client
  cannot be built (missing key, import error), the existing warning/error logs are
  upgraded to a single `log_error_event(error_type="earnings_gate_unusable",
  recoverable=True)` so "enabled but broken" is a queryable error event, not a
  debug whisper.
- **Cache moves to module scope:** `_EARNINGS_CACHE: Dict[str, Dict]` and
  `_EARNINGS_FAILURE_CACHE: Dict[str, datetime]` at module level, plus
  `clear_earnings_cache()` for tests. Instances read/write the shared dicts;
  TTL/failure-window logic unchanged. Rationale: `/scan` builds a fresh scanner
  (and would build a fresh service) per request, so an instance cache re-fetches
  the whole universe every scan (~182 calls/day); module scope makes
  `earnings.cache_ttl_hours: 24` real within an instance's lifetime. The roller's
  per-cycle service instance shares the same cache for free.
- `is_earnings_within_n_days`, `get_next_earnings_date`, `get_earnings_proximity`:
  **unchanged behavior** (roller contract preserved verbatim).

### 2. `HistoricalEarningsCalendar` — same tri-state surface

`src/backtesting/engine/historical_earnings.py`:

- **Add `earnings_within(self, symbol, n_days) -> Optional[bool]`:** symbol present
  in the table → `bool` from the existing inclusive-both-ends window arithmetic
  (frozen-clock `_today()`); symbol **absent** from the table → `False` **plus**
  `symbols_without_data.add(symbol)` (the existing reporting mechanism).
- **Replay fails open on table gaps, deliberately** — the one asymmetry with live,
  stated with its rationale: a replay "outage" is not a live risk, and returning
  `None` (block) for a symbol missing from the table would silently zero out that
  symbol's entire replay — a pessimistic measurement bias corrupting verdicts. The
  gap is *reported* (`symbols_without_data` already surfaces in the report path)
  so the operator refreshes the table (`tools/backtesting/fetch_earnings_table.py`)
  instead of reading a biased verdict. The committed table covers all 14 universe
  symbols with dates through 2026-10-27; a replay approaching the horizon inherits
  a mild optimistic bias at the edge — the table's `generated` stamp plus the
  report line make that visible.
- Existing methods and the frozen-clock guard: unchanged.

### 3. `OptionsScanner` — the gate, both legs

`src/data/options_scanner.py`:

- **Constructor:** add `earnings_calendar: Optional[object] = None` alongside
  `allow_bigquery` (same explicit-injection seam, same rationale block — a
  `clock.is_frozen()` keyed gate is rejected for the reasons already on the page
  at `__init__`). Resolution:
  - param provided → use it (the simulator's path);
  - param `None` and `config.earnings_enabled` → `EarningsCalendarService(config)`;
  - param `None` and not enabled → `self.earnings_calendar = None` (gate off).
- **One helper, one predicate for both legs** (the symmetry is load-bearing):

  ```python
  def _earnings_gate(self, symbol: str) -> Optional[str]:
      """None = clear to trade; else the block reason (a decision-record REASON_*)."""
      if self.earnings_calendar is None:
          return None
      within = self.earnings_calendar.earnings_within(
          symbol, self.config.earnings_blackout_days)
      if within is None:
          return REASON_EARNINGS_UNKNOWN     # fail closed: could not tell
      return REASON_EARNINGS_BLACKOUT if within else None
  ```

- **Put leg** — in `scan_for_put_opportunities`, first check inside the
  per-suitable-stock loop (before `_has_existing_position`; both are network-or-
  cache checks, and gating first means the event count reads as full-universe
  earnings exposure, held or not):

  ```python
  gate_reason = self._earnings_gate(symbol)
  if gate_reason:
      logger.warning("Skipping put scan - earnings blackout",
                     event_category="trade",
                     event_type=("put_scan_skipped_earnings_blackout"
                                 if gate_reason == REASON_EARNINGS_BLACKOUT
                                 else "put_scan_skipped_earnings_unknown"),
                     symbol=symbol,
                     blackout_days=self.config.earnings_blackout_days,
                     **self.earnings_calendar.get_earnings_proximity(symbol))
      continue
  ```

- **Call leg** — in `scan_for_call_opportunities`, in the per-position ladder
  **after** the `shares < 100` not-eligible check and **before** cost-basis
  resolution (a blacked-out symbol should not spend a resolver call and a BigQuery
  cross-check; `not_eligible` stays the more-structural first rung). Emits the
  symmetric `call_scan_skipped_earnings_blackout` / `…_unknown` event with the same
  enrichment, **plus** the decision-record row:

  ```python
  recorder.record(symbol, OUTCOME_BLOCKED, gate_reason, **labels)
  recorded_symbols.append(symbol)
  continue
  ```

  (`labels` here is the pre-floor dict — `shares`, `current_price`,
  `uncovered_days`; no `cost_basis_per_share`/`underwater`, per DD-4.)
- **Behavior contract — what must NOT change:** opportunity dict shape (no new
  keys); `run_id` threading; `stamp_decision_labels` flow; the ordering and
  semantics of every existing ladder rung (`not_eligible` → [gate] → divergent →
  unresolved → chain scan); `_has_existing_position` (FC-069 item 12's turf);
  scanner behavior when `earnings.enabled: false` is byte-identical to today.
  `/scan`, CLI `--command scan`, and the simulator all construct through the same
  two seams and get the gate consistently.

### 6. The exposure audit — pre-build gate, committed script

**This runs BEFORE wiring begins** (FC-069 card 4's marked query, required plan
input; currently blocked on expired gcloud auth — build step 0 is `gcloud auth
login`/ADC refresh). Committed as
`tools/diagnostics/fc013_earnings_exposure_audit.py` (reuse value: it is also the
recurring detective query for "did anything trade inside a window", given the
log-sink to BQ is dead and events age out of Cloud Logging in 30 days).

Mechanics: load the point-in-time calendar via
`HistoricalEarningsCalendar.from_table()` (the committed
`src/backtesting/data/earnings_dates.json` — reproducible, no Finnhub dependency),
pull all option sell-to-open fills, join in pandas. The fills pull, verbatim:

```sql
SELECT activity_id, symbol, underlying, option_type, side, qty, price,
       premium_total, strike_price, expiration,
       DATE(transaction_time, 'America/New_York') AS fill_date
FROM `options_wheel.trades_from_activities`
WHERE activity_type = 'FILL'
  AND option_type IS NOT NULL
  AND side = 'sell'
ORDER BY transaction_time
```

(`side='sell'` on an option FILL is sell-to-open for this strategy — it holds no
long options to sell-to-close; the script asserts that by checking no prior long
position, and reports any exception rather than silently miscounting.)

Per fill, against the calendar's dates for `underlying`: compute
`days_to_next_earnings = min({e − fill_date : e ≥ fill_date})` and
`spans_earnings = any(fill_date ≤ e ≤ expiration)`. Report, put and call legs
separately:

1. **Within-window exposure counts** for N ∈ {1, 2, 3, 5}.
2. **Span-predicate exposure count** (DD-3's deferred alternative).
3. **Realized P&L of exposed positions vs the book's average** — joined via
   `trades_with_outcomes` (per-position outcomes) on the opening fill.

## Risks & mitigations

- **Fail-closed outage = no opens account-wide that day.** Bounded: one day of
  foregone 7-DTE premium; closes/monitor unaffected; 1h failure cache retries
  within the hour; loud `*_unknown` events. Accepted per DD-2; restated here so
  sign-off sees it.
- **Deploying near an earnings date with a cold cache** (rev 1's GOOGL risk, still
  real): first scan after deploy pays ~14 Finnhub fetches; a transient hiccup then
  blocks symbols as unknown. Mitigation: deploy outside market hours; the
  post-deploy verification scan (§Rollout) confirms the cache is warm and events
  are the expected type before the next scheduled scan.
- **`/scan` latency**: +2–6s worst case on cold cache vs ~18.5s baseline —
  measured expectation, well inside Cloud Run timeouts; steady-state ~0ms.
  Verified in the post-deploy scan.
- **A blocked symbol every scan for 2 days reads as "scanner broke" to a future
  reader.** Mitigation: decision rows + events name the reason; `docs/gates.md`
  documents the gate; the dashboard reason string renders (build-step check,
  DD-4).
- **Base-branch drift**: this builds on `fc-068/engine-path-deletion` pre-merge. If
  FC-068's confirmation-pass fixes touch the scanner, rebase re-verifies §3's
  ladder placement (the gate sits between two named rungs — symbol names, not
  lines, are the contract).
- **Finnhub data quality** (wrong/moved earnings dates): unchanged risk from
  FC-007; the 24h TTL bounds staleness; the audit script doubles as the
  retrospective detector for any date Finnhub had wrong.
