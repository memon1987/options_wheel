## Rev 1 (superseded 2026-08-01)

Rev 1 (2026-04-29) responded to the GOOG incident by wiring the earnings gate into
`PutSeller.find_put_opportunity` and `CallSeller.evaluate_covered_call_opportunity`,
injected from `WheelEngine`. **Every one of those wiring targets is deleted by FC-068**
(`docs/plans/fc-068.md` §1–3): the engine builds no sellers, and both seller-side
opportunity producers are gone. Production trades via `/scan` → `OptionsScanner` →
GCS blob → `/run` → `ExecutionEngine` → the sellers' `execute_*` methods, and the
backtest now replays that exact pipeline.

**What survives from rev 1:** the `EarningsCalendarService` service-layer decisions
(Finnhub, caching, failure cache, `get_earnings_proximity` enrichment); the
fail-closed instinct (operator-reconfirmed at FC-069 sign-off); activating the
`earnings.blackout_days` knob; the test-matrix shape (gate fires / allows / blocks on
failure / no-op when disabled); the `docs/gates.md` deliverable.

**What rev 2 corrects in rev 1, beyond the deleted wiring targets:**

1. **Rev 1's fail-closed spec (§3) was buggy as written.** It flipped
   `is_earnings_within_n_days`'s error paths to return `True` — but that method's
   `days_until is None` branch conflates two different states: *"Finnhub fetch
   failed"* (`_fetch_earnings` returned `None`) and *"no earnings scheduled in the
   next 90 days"* (a successful fetch cached as `{"date": None}`). Flipping the
   `None` branch would have blocked every known-clear symbol — an account-wide
   brick on normal days. Rev 2 introduces a tri-state method instead (§Approach 2).
2. **Deleting `earnings_avoidance_days` moved to FC-069's sweep** (item 4 decision
   line, binding). This plan does not touch it.
3. **Rev 1's fail-closed flip changed the roller's behavior.** Operator decision
   (FC-069): the roller keeps its existing gate unchanged. Rev 2 confines the new
   semantics to the new gate; `is_earnings_within_n_days` is untouched.

## Context

**Two incidents on record, same root cause: no earnings gate has ever existed on any
path that trades.**

- A GOOGL cash-secured put executed **2026-04-28**, the day before Google's
  earnings (**2026-04-29**, confirmed in the committed earnings table).
- An AAPL covered call was sold the week of **2026-07-27**, days before Apple's
  earnings (**2026-07-30**, confirmed in the committed table). Note what this
  geometry means: a Monday 07-27 fill sits at `days_until = 3` — **outside the
  untuned `blackout_days: 2` default**. The flagship incident is not demonstrably
  blocked by the default knob value; DD-3's acceptance criterion exists because of
  this.

Verified against the post-FC-068 tree (`origin/fc-068/engine-path-deletion`, tip
`c72127a` — the base this plan builds on): zero earnings references in
`src/data/options_scanner.py`, `src/strategy/put_seller.py`,
`src/strategy/call_seller.py`, `src/strategy/execution_engine.py`. The only earnings
consumers are the Friday roller (`CallRoller.should_roll` — the `earnings_blackout`
gate, structurally no-op'd by the quote-key bug, FC-066) and the backtest's roller
seam (`HistoricalEarningsCalendar`, threaded through `WheelEngine` in
`simulator.py`). The `earnings.*` knobs (`settings.yaml`: `enabled: true`,
`cache_ttl_hours: 24`, `blackout_days: 2`, `lookahead_days: 90`) read as live and
gate nothing that opens a position.

**Operator decisions (FC-069 item 4 sign-off, 2026-08-01 — binding, not relitigated
here):**

- The earnings gate is a key part of the gating strategy. **REVIVE.**
- Gate **both** put opens and call opens. The roller keeps its existing gate.
- **Live and backtest coverage.** Post-FC-068 the simulator replays the scanner
  pipeline, so a scanner-layer gate applies in replays via the
  `HistoricalEarningsCalendar` seam — threaded explicitly (the FC-068-created
  obligation this plan discharges).
- Finnhub service, `FINNHUB_API_KEY`, and the `earnings.*` knobs stay.
- The dead `risk.gap_risk_controls.earnings_avoidance_days` knob dies in FC-069's
  sweep, not here.

**New findings from this re-plan (verified against `c72127a`; items 3–5 added at
rev 2.1 from the plan reviews):**

- **The 24h earnings cache is fictional at request scope — twice over.**
  `EarningsCalendarService` keeps `_cache` on the instance; `/scan` constructs a
  fresh `OptionsScanner` per request (`cloud_run_server.py`, `trigger_scan`). And
  the service runs with **min-instances=0** (`COST_OPTIMIZATION.md`; live-verify
  `gcloud run services describe` at build), so even a module-scope cache mostly
  dies between the hourly scans. §Approach 1 layers a durable GCS cache under a
  module-scope L1, which is what finally makes `earnings.cache_ttl_hours` real.
- **The FC-069 card's Finnhub-volume aside is backwards.** Card 4(c)(i) says
  scanner-side placement "spares Finnhub calls for symbols that produce no
  candidates" — in fact selection-side would need *fewer* lookups. The placement
  decision does not rest on call volume either way.
- **`EarningsCalendarService.__init__` crashes rather than degrades on a missing
  key** (rev 2.1, both reviewers): the early `return` on empty `finnhub_api_key`
  exits before `_enabled` / `_cache_ttl_hours` / `_lookahead_days` are set, so
  every subsequent method call raises `AttributeError` — which the scanner's broad
  `except` would misfile as `scan_failure`, producing zero opportunities *and zero
  unknown-events/rows*. §Approach 1 fixes the constructor; a named test pins the
  degraded path.
- **The committed earnings table is horizon-dead today** (rev 2.1, trader HIGH-3):
  generated 2026-07-18; of the 11 reporting symbols, only UNH (2026-10-27), NVDA
  (08-26), AMD and PFE (08-04) extend past 2026-08-01 — F's last date (07-28),
  GOOGL's (07-22), KMI's, MSFT's, AMZN's, AAPL's and VZ's are already past. And
  horizon exhaustion is **silent**: a present symbol with only past dates answers
  `False` (allow), and `symbols_without_data` fires only for *absent* symbols.
  §Approach 2 adds a horizon report; §Rollout puts a table refresh before the
  audit. (IWM/QQQ/SPY are present-with-empty by design — ETFs have no earnings.)
- **No alert policy matches any earnings event** (rev 2.1, reliability D2):
  `deploy/monitoring/` enumerated — `cost_basis_alert_policy.json` matches exactly
  two `call_scan_skipped_cost_basis_*` strings; `alert-policy.yaml` has empty
  `notificationChannels`. Rev 2's DD-6 claim that `earnings_fetch_failed` "flows
  through the existing FC-030 error-event alerting baseline" was **false**. DD-6
  is rewritten: fail-closed **and** alert.

## Goals

- One earnings gate, at the scanner, covering **both** legs: a symbol within the
  blackout window produces no put opportunities and no call opportunities.
- The same gate object works in production (`EarningsCalendarService`, Finnhub) and
  in replays (`HistoricalEarningsCalendar`, committed point-in-time table) through
  one injected seam.
- **Fail closed on unknown, and loudly**: when the calendar cannot answer (Finnhub
  outage, missing key), the symbol is skipped — with events that distinguish
  "blocked by real earnings" from "blocked because we could not tell", **and a
  deployed alert policy on the unknown-state events** (DD-6).
- Every skip is legible: structured events on both legs, a P4 decision-record row on
  the call leg, replay-tally mappings on both legs.
- The blackout window **value** is chosen by the operator on data, not inherited —
  and whatever is chosen **must demonstrably block both incidents on record**
  (DD-3 acceptance criterion).
- `docs/gates.md` ships: the live-path gate inventory FC-069 items 3/14 plan to
  point at.

## Non-goals

- Deleting `earnings_avoidance_days` (FC-069 sweep, binding).
- Unifying `rolling.earnings_blackout_days` with `earnings.blackout_days`, or any
  change to the roller's gate (§Design decision 5: FC-066's turf, item 13 HOLD).
- Per-symbol blackout windows (universe of 14; single global knob, as rev 1 decided).
- Closing existing positions ahead of earnings (conflicts with FC-010
  assignment-tolerance; the wheel takes assignment).
- Extending the P4 `decision_events` table to the put leg. That table is by design
  the per-held-symbol *covered-call* decision record; put-side legibility here is
  events + tally + the committed audit script (§Approach 6). A put-side decision
  table is its own FC if ever wanted.
- New alerting **beyond** the one earnings-gate policy DD-6 now specs; a card-16
  detective check stays FC-069's turf.
- `/monitor` (closes reduce risk; never gated) and `/run` (gate is upstream, §DD-1).

## Design decisions

### DD-1 — Placement: scanner-side symbol gate (both legs), not selection-side, not both

**Chosen:** a symbol-level gate inside `OptionsScanner`, before opportunity
construction on each leg.

**Rejected — selection-side drop (`select_batch`, new `DROP_EARNINGS_BLACKOUT`):**

- `/run` has no earnings data and no natural place to get it: either
  `ExecutionEngine` grows its own Finnhub surface (a second copy of the outage
  problem, in the process that places orders), or the scan stamps proximity onto
  each opportunity and selection reads it — which is scan-time evaluation wearing a
  selection costume, plus blob plumbing.
- `DROP_REASONS` is FC-038's model for **batch-resource contention** — shares,
  buying power, duplicate-underlying — evaluated against *this batch*. Earnings is
  a symbol-level *policy* fact known before any chain is fetched. Wedging it into
  the drop model misfiles it.
- Selection-side wastes the scan: chains fetched, opportunities built and ranked
  for a symbol that cannot trade, plus (call leg) a BigQuery cost-basis cross-check
  spent on it.
- Observability is not better there: the call leg's drop would reach decision
  records via `/run`, but the scan-side gate reaches them too (§DD-4), and the put
  leg has no decision-record machinery on either side.

**Rejected — gate at both:** no incremental protection. `blackout_days` is a
days-granular predicate; between `/scan` and `/run` sit ≤30 minutes
(`opportunity_max_age_minutes`), inside market hours, never crossing midnight — the
predicate cannot change value in that window. Cost: a second Finnhub dependency
surface and a second failure-semantics decision, for nothing.

**Finnhub volume / latency, derived against the real topology (rev 2.1 — rev 2's
numbers assumed ~13 scans/day and warm instances; production runs 6 scans/day,
hourly :00 from 10:00–15:00 ET, on min-instances=0, so instances are typically
reaped between hour-blocks and a module cache alone is cold nearly every scan):**

- Gate consults the calendar once per put-side *suitable* stock (≤14) and once per
  call-side held symbol (≤7, overlapping) — ≤14 unique symbols per scan.
- **Without durable storage:** ~6 cold scans × 14 = **~84 Finnhub calls/day worst
  case**, each scan paying +2–6s of sequential fetches on the ~18.5s baseline —
  every scan, not once a day. "Cache hits, ~0ms" was a per-instance truth that is
  operationally false at min-instances=0.
- **With the durable GCS cache (§Approach 1, adopted):** ~14 fetches per 24h
  account-wide; the other five scans read one small GCS blob (~100–300ms). Finnhub
  free-tier limit is 60 calls/min; both shapes are well inside it.

**The NVDA-silent-exclusion lesson is honored, not waived:** a scanner skip here is
*never* silent — call leg writes a decision-record row (§DD-4), both legs emit
structured events, both events are tally-mapped for replays (§Approach 5), and the
unknown-state events are alerted (DD-6).

### DD-2 — Failure semantics: fail closed on unknown, via a new tri-state method — plus the alert that bounds it

**Chosen: fail-closed, with a deployed alert on the unknown state (DD-6).** When
the calendar cannot answer for a symbol, that symbol is skipped for this scan, on
both legs, with a distinct "unknown" event.

The options, weighed honestly:

- **Fail-closed + alert** (chosen — rev 2.1; rev 2 weighed only three options and
  under-stated the blast radius). A *transient* Finnhub outage at scan time means
  no opens account-wide for the affected scans — bounded and cheap: foregone
  7-DTE premium for part of a day, next scan retries after the 1h failure cache,
  and the durable cache (§Approach 1) means an outage only bites at all when the
  cached dates are >24h stale. But a **persistent** cause — key wiped by a
  `--set-env-vars` deploy, key revoked, Finnhub plan lapsed — blocks **all opens
  indefinitely, not for "one day"**. Nothing self-heals that; the alert is what
  bounds it. Hence the policy in DD-6 is a required deliverable of this FC, not an
  optional follow-up.
- **Fail-open-with-alert** (rejected): trades through outages ungated — the gate is
  silently absent exactly when its input is unverifiable. This codebase's signature
  disease is controls that read as live and fail open (`STATE_STORAGE_BUCKET`, the
  min-hold gate, the pre-FC-065 floor); FC-069 item 8's standing note exists
  because of it. An alert does not stop the trade.
- **Fail-closed-with-stale-cache-grace** (rejected as a *separate mechanism*, and
  rev 2's rejection rationale is corrected): rev 2 said a morning outage meets a
  cold cache "with nothing to be graceful with" — which is an argument **for
  durable storage, not against grace**. With the GCS cache adopted, the TTL itself
  *is* the grace: an entry fetched yesterday remains valid through today's outage.
  No second mechanism needed.

**Mechanism — do not flip the existing method.** `is_earnings_within_n_days` stays
exactly as-is (the roller's gate, operator-decided unchanged; and its `None` branch
conflates "clear" with "unknown", rev 1's bug). New method on both calendar classes:

```
earnings_within(symbol, n_days) -> Optional[bool]
    True   — next earnings date within the window (block)
    False  — fetch succeeded, no earnings within the window (allow)
    None   — could not determine (fetch failed / no client / no key) → gate blocks
```

**Enabled-but-unusable degrades loudly — after the constructor fix (rev 2.1).**
As written today the no-key path does not degrade at all: it **crashes** (see
Context finding 3), and rev 2's claim that "every scan emits
`*_skipped_earnings_unknown`" described behavior the code could not produce. The
fixed contract (§Approach 1): construction with `earnings.enabled: true` and a
missing/unusable key initializes every attribute, logs one
`earnings_gate_unusable` error event, and leaves `_client = None`; thereafter
`earnings_within` returns `None` for every symbol, so every scan skips every
symbol with `*_skipped_earnings_unknown` events and `(blocked, earnings_unknown)`
rows — no exception, no `scan_failure` misfile. That posture is FC-069 item 8's
standing note: a configured-but-unresolvable dependency must fail loudly, never
silently no-op. `earnings.enabled: false` disables the gate entirely — *disabled*
and *broken* are different states with different behavior, by design.

I judge fail-closed decided, not a blocking operator question: the operator
confirmed the instinct survives (FC-069 card 4), and the blast radius —
transient-bounded by cache+retry, persistent-bounded by the alert — is restated in
§Risks so sign-off sees it.

### DD-3 — Blackout window: predicate pinned; value is a data-informed operator call with a hard acceptance criterion (pre-build gate)

**Predicate, pinned exactly:** block symbol S when
`0 <= (next_earnings_date(S) − today) <= N` in **calendar days**, where `today` is
`date.today()` live and `clock.now().date()` in replays. Pre-earnings only:

- **Day-of (0) is blocked** — most earnings in this universe are AMC; day-of selling
  is the maximum-exposure trade.
- **Post-earnings is not covered.** The service only looks forward
  (`_from=today`), so a symbol that reported yesterday resolves to next quarter.
  This is deliberate, not an accident of the API: the day after earnings is
  IV-crush territory — elevated premium already collapsing, gap risk realized —
  and blocking it would cost the wheel some of its best entries.
- **Calendar days, not trading days** (rejected alternative): trading-day semantics
  give uniform protection across weekdays but add a market-calendar dependency to
  the gate. With calendar days, a Monday AMC reporter under N=2 is "blocked"
  Sat/Sun/Mon — effectively one trading day of protection — while a Wednesday
  reporter gets two. Stated and accepted; if the operator wants uniform trading-day
  protection, that is a knob-semantics change on top of this gate, not a different
  gate.

**Value: `blackout_days: 2` was never tuned — and the default demonstrably fails
the flagship incident.** AAPL reported 2026-07-30; any fill on Monday/Tuesday of
the incident week sits at `days_until` 3–2, so a Monday fill **passes** N=2. The
exposure audit (§Approach 6) is a **pre-build gate**: it runs before any wiring is
written (blocked today on expired gcloud auth — build step 0 is re-auth, after the
table refresh), pins **both incidents' exact fill dates by name** and reports each
incident's `days_until`, and its output goes to the operator with the window
decision.

**Acceptance criterion (binding on the build):** *the chosen configuration must,
applied retroactively, block both incidents on record — the GOOGL put filled
2026-04-28 (earnings 2026-04-29) and the AAPL covered call filled the week of
2026-07-27 (earnings 2026-07-30, exact fill date pinned by the audit). If no N in
the audited bucket set blocks both at acceptable foregone-premium cost, the span
predicate — or N ≥ the demonstrated gap — escalates INTO this FC's build scope,
not into a follow-up.* A gate that ships unable to stop the incidents that
motivated it is ceremony, and this FC family exists to end ceremony.

**The span predicate is nearly a knob value, not an architecture change (rev 2.1
correction to rev 2's "deferred" framing).** For a 7-DTE seller, days-based
blackout under-covers: a put sold 5 days before earnings with 7 DTE *holds through*
the event, ungated at N=2. The arguably-correct predicate is "block when the
candidate's expiration ≥ the next earnings date" — opportunity-level, needing the
candidate's expiry. **But for a uniform 7-DTE book, `days_until ≤ 7` and
`expiry ≥ earnings` converge — N = DTE *is* the span predicate.** The audit bucket
set therefore includes N=7 (§Approach 6), and "span protection" is on the
operator's menu as a knob value first, with the per-candidate implementation held
in reserve for a mixed-DTE future. This resolves rev 2's tension between "span is
correct" and "span is deferred": it is deferred *as machinery*, available *as a
value*.

### DD-4 — Decision-record integration: two new reasons under `blocked`, schema untouched

- `REASON_EARNINGS_BLACKOUT = "earnings_blackout"` and
  `REASON_EARNINGS_UNKNOWN = "earnings_unknown"`, both added to
  `ALLOWED_REASONS[OUTCOME_BLOCKED]` in `src/data/decision_record.py`. Two reasons,
  not one: a row that says "earnings blackout" when Finnhub was down is a mislabel,
  and the closed vocabulary exists precisely so rows cannot misfile
  (`UnknownDecisionOutcome`'s reason for being).
- **No new outcome** — `blocked` already means "a policy gate terminated this
  symbol at scan"; the floor reasons prove the shape.
- **No schema change.** `decision_events` columns are untouched; earnings detail
  (`next_earnings_date`, `days_until`, `earnings_hour`) rides the structured log
  event, not the record row. The `_LABEL_FIELDS` labels
  (`shares`/`current_price`/`uncovered_days`) ride as usual;
  `cost_basis_per_share`/`underwater` are absent on earnings-blocked rows because
  the gate fires *before* basis resolution (§Approach 3) — nullable columns, same
  as several existing row shapes.
- Dedup key `(run_id, symbol, stage)` and the `sold`-wins ordering are unaffected.
- **Closed-enum tests:** `tests/test_decision_record.py`'s enum class gains
  `validate_outcome(OUTCOME_BLOCKED, REASON_EARNINGS_BLACKOUT/…UNKNOWN)` acceptance
  cases; the cross-pairing rejection test (`dropped` × floor reason, etc.) is
  extended to assert `validate_outcome(OUTCOME_DROPPED, REASON_EARNINGS_BLACKOUT)`
  still raises. No existing assertion weakens.
- **Cascading-impact check (docs/CLAUDE.md rule), names corrected at rev 2.1:** the
  dashboard reader is `uncovered_decisions_sql`
  (`dashboard/backend/services/bigquery.py:39`) — selects `reason` as a free
  string, additive-safe. The consuming card is
  `dashboard/frontend/src/components/v2/DrawdownPauseCard.tsx`, which renders
  `reason` free-form. Build step: confirm free-form rendering holds; add display
  labels for the two new reasons only if a mapping exists.

### DD-6 — Alerting: one dedicated earnings-gate alert policy (rev 2.1 — rewritten; rev 2's premise was false)

Rev 2 leaned "no new alert" on the claim that `earnings_fetch_failed` error events
"flow through the existing FC-030 error-event alerting baseline." **Verified
false** (Context finding 5): no deployed policy matches any earnings event string,
and `alert-policy.yaml` carries empty `notificationChannels`. Without a policy, a
persistent unknown-state (key wiped/revoked) blocks all opens **indefinitely and
silently** — the exact "gate reads as protective, operator learns weeks later"
failure this plan exists to end, pointed the other direction.

**Deliverable:** `deploy/monitoring/earnings_gate_alert_policy.json`, modeled
verbatim on `cost_basis_alert_policy.json` (the FC-065 P1 precedent):

- **Match filter:** `jsonPayload.event_type` ∈
  {`put_scan_skipped_earnings_unknown`, `call_scan_skipped_earnings_unknown`,
  `earnings_gate_unusable`} OR the same three as `textPayload:` substrings —
  payload matched both ways, and **no severity clause** (Cloud Run captures stderr
  as plain text with EMPTY severity; a `severity>=WARNING` clause matches nothing —
  verified by the FC-030 fire drill 2026-07-18).
- **Channel:** the existing verified email channel the cost-basis policy uses.
- **Documentation content:** what the unknown state means (Finnhub outage vs key
  wiped vs plan lapsed), triage (`gcloud logging read` on the three event types;
  check `FINNHUB_API_KEY` on the live revision; check Finnhub status), and the
  reminder that fail-closed is correct behavior, not a bug to work around — plus
  the DD-7 env lever as the emergency response.
- **Not alerted:** `*_skipped_earnings_blackout` — a blackout skip is the gate
  working; normal operation, visible in decision records and events.

### DD-7 — Kill switch: env-var override, because baked-config rollback rides a pipeline that once sat red for 11 days (rev 2.1)

`earnings.enabled` lives in `settings.yaml`, baked into the image — "atomic
config rollback" in rev 2 actually meant commit → Cloud Build → deploy, behind the
same pipeline whose silent red build delayed FC-031 by 11 days. **Adopted:**
`config.earnings_enabled` honors an env override — `EARNINGS_ENABLED` (unset →
yaml value; set → parsed boolean wins). Disabling the gate in production becomes:

```
gcloud run services update options-wheel-strategy --update-env-vars EARNINGS_ENABLED=false
```

— one command, new revision in ~1 minute, no Cloud Build, no code commit.
(**`--update-env-vars`, never `--set-env-vars`** — the latter wipes the whole env
set, the documented gotcha that is itself one of this gate's persistent-failure
scenarios.) The yaml key remains the default and the documented home; the env var
is the emergency lever, documented in the alert policy's triage text.

### DD-8 — Replay semantics of `earnings.enabled`: policy follows config, injection supplies only data (rev 2.1)

Rev 2 left this ambiguous: as specced, an injected calendar always gated, so a
live rolloff (`enabled: false`) would leave replays gated — a live/replay
divergence on exactly the FC-048 fidelity axis. **Decided:** the scanner's gate
consults `config.earnings_enabled` **regardless of injection** — an injected
calendar substitutes the *data source* (Finnhub vs point-in-time table), never the
*policy*. `earnings.enabled: false` in the active config disables the gate in
production and in replays alike; a what-if replay with the gate forced on/off is a
config override, the same way every other knob is what-if'd. Pinned by test 10b.
**Noted, not changed:** the roller seam has the pre-existing inverse quirk
(`run_rolling_cycle` checks `earnings_enabled` only when constructing its own
service; an injected calendar bypasses the check) — recorded in `docs/gates.md` as
FC-066's inheritance, untouched here.

## Proposed approach

All file/line references against `origin/fc-068/engine-path-deletion` @ `c72127a`.
Symbol names are the contract; lines will drift at rebase.

### 1. `EarningsCalendarService` — tri-state method, constructor fix, two-layer cache

`src/api/earnings_calendar.py`:

- **Constructor fix (rev 2.1 — required, both reviewers):** initialize **every**
  attribute (`_cache_ttl_hours`, `_lookahead_days`, `_enabled`, `_client = None`)
  *before* any early exit. The missing-key and failed-import paths no longer
  return a half-built object; they log one
  `log_error_event(error_type="earnings_gate_unusable", recoverable=True)` (when
  `earnings.enabled` is true) and leave `_client = None`. Every public method is
  callable on every construction path — the degraded service *answers*, it never
  raises.
- **Add `earnings_within(self, symbol: str, n_days: int) -> Optional[bool]`:**
  - `not self._client` → `None` (unusable ⇒ unknown ⇒ caller blocks). The scanner
    never consults the calendar when the gate is disabled (§3), so this method may
    assume enabled; the `None` is defense in depth.
  - Cached/fetched entry with `date is None` (successful fetch, nothing in the 90d
    lookahead) → `False` (known clear).
  - Entry with a date → `0 <= (date - date.today()).days <= n_days`.
  - `_fetch_earnings` returned `None` (failure, incl. failure-cache window) →
    `None` (unknown).
- **Two-layer cache (rev 2.1 — durable layer adopted; see DD-1's topology
  numbers):**
  - **L1, module scope:** `_EARNINGS_CACHE: Dict[str, Dict]` and
    `_EARNINGS_FAILURE_CACHE: Dict[str, datetime]` at module level, plus
    `clear_earnings_cache()` for tests. Survives per-request scanner construction
    within an instance.
  - **L2, GCS blob:** one JSON object (`earnings_cache.json`, per-symbol entries
    `{date, hour, fetched_at}`) in the same bucket the opportunity store uses —
    read-through on L1 miss, write-through after any successful fetch batch.
    Entries respect the same `cache_ttl_hours` TTL. **GCS unavailability is a
    cache miss, never a block** — the ladder is L1 → L2 → Finnhub → (unknown);
    only Finnhub's answer (or its absence) determines gate state. Rationale for
    adopting: at min-instances=0 a memory-only cache is cold nearly every scan
    (≈84 calls/day, +2–6s per scan, and a morning outage meets an empty cache);
    the blob makes the 24h TTL real (~14 fetches/day) and shrinks the outage
    blast radius to "Finnhub down **and** cached dates >24h stale". Cost: one
    small GCS read per scan (~100–300ms) on an already-GCS-dependent path, and
    ~40 lines reusing the opportunity store's client/bucket plumbing.
  - **Concurrency posture, stated (reliability D12):** `/scan` runs under
    `strategy_lock`, so cache mutation is de facto serialized — the safety rests
    on that lock, recorded here so a future concurrent caller re-evaluates.
    Cheap hardening specced anyway (trader MEDIUM-7): eviction uses
    `.pop(symbol, None)`, never bare `del`, so a racing reader cannot KeyError.
- **Empty-200 ambiguity, stated and accepted with visibility (trader MEDIUM-6 /
  reliability D9):** a Finnhub 200 with an empty `earningsCalendar` is cached as
  known-clear (`{"date": None}`). Correct for ETFs (IWM/QQQ/SPY) and for genuine
  quiet windows — but a symbol-coverage regression on Finnhub's side would read
  as *permanently clear*: silent fail-open for that symbol. Accepted (the
  alternative — treating empty as unknown — bricks every ETF and quiet-window
  symbol). Visibility: the fetch's debug log gains `calendar_empty=True` on this
  path, and the audit script (§6) doubles as the retrospective detector — any
  fill inside a *table*-known window that Finnhub called clear shows up there.
- `is_earnings_within_n_days`, `get_next_earnings_date`, `get_earnings_proximity`:
  **unchanged behavior** (roller contract preserved verbatim).

### 2. `HistoricalEarningsCalendar` — same tri-state surface, plus the horizon report

`src/backtesting/engine/historical_earnings.py`:

- **Add `earnings_within(self, symbol, n_days) -> Optional[bool]`:** symbol present
  in the table → `bool` from the existing inclusive-both-ends window arithmetic
  (frozen-clock `_today()`); symbol **absent** from the table → `False` **plus**
  `symbols_without_data.add(symbol)` (the existing reporting mechanism).
- **Horizon exhaustion becomes reportable (rev 2.1 — trader HIGH-3 / reliability
  D11):** a symbol *present* with only *past* dates currently answers exactly like
  known-clear — silent fail-open at the table's edge, and most of the table's
  reporters are past-edge **today** (Context finding 4). Add
  `horizon_for(symbol) -> Optional[date]` (the symbol's last table date; `None`
  for absent/empty) and a `symbols_past_horizon` set populated when
  `next_earnings_date` finds only past dates for a present, non-empty symbol. The
  simulator surfaces both sets in the run report: **a replay whose window end
  exceeds a traded symbol's horizon date is flagged like a data gap**, naming the
  symbol and its last covered date. ETF entries (present-with-empty) are
  legitimately clear forever and are excluded from the horizon report by the
  non-empty condition.
- **Replay fails open on table gaps, deliberately** — the one asymmetry with live,
  stated with its rationale: a replay "outage" is not a live risk, and returning
  `None` (block) for a symbol missing from the table would silently zero out that
  symbol's entire replay — a pessimistic measurement bias corrupting verdicts. The
  gap is *reported* (both sets above) so the operator refreshes the table
  (`tools/backtesting/fetch_earnings_table.py`) instead of reading a biased
  verdict.
- Existing methods and the frozen-clock guard: unchanged.

## Risks & mitigations

- **Fail-closed unknown-state: transient vs persistent, stated honestly
  (rev 2.1).** *Transient* Finnhub outage: bounded — with the L2 cache, only
  symbols whose cached dates are >24h stale block; 1h failure cache retries;
  foregone 7-DTE premium for part of a day. *Persistent* cause (key wiped/revoked,
  plan lapsed): **blocks all opens indefinitely** — bounded only by the DD-6
  alert, which is why the alert policy is a required deliverable, and by the DD-7
  env lever for the operator's response.
- **Deploying near an earnings date with a cold cache** (rev 1's GOOGL risk, still
  real): first scan after deploy pays up to ~14 Finnhub fetches; a transient
  hiccup then blocks symbols as unknown. Mitigation: deploy outside market hours;
  the post-deploy verification scan confirms the L2 blob is populated and events
  are the expected type before the next scheduled scan.
- **`/scan` latency**: worst case (cold L1+L2, first scan after deploy) +2–6s of
  sequential fetches on the ~18.5s baseline; steady state one L2 read
  (~100–300ms) per scan and ~14 fetches/day account-wide. Verified in the
  post-deploy scan. (Numbers derived against the real 6-scan/min-instances=0
  topology — DD-1.)
- **A blocked symbol every scan for N days reads as "scanner broke" to a future
  reader.** Mitigation: decision rows + events name the reason; `docs/gates.md`
  documents the gate; the dashboard reason string renders free-form
  (`DrawdownPauseCard.tsx` — build-step check, DD-4).
- **Base-branch drift**: this builds on `fc-068/engine-path-deletion` pre-merge. If
  FC-068's confirmation-pass fixes touch the scanner, rebase re-verifies §3's

- **Finnhub data quality** (wrong/moved dates; empty-200 coverage gaps — §1's

- **GCS cache blob as a new dependency**: read failure falls through to Finnhub
