## Context

Alpaca's paper-trading engine occasionally settles deep-ITM option exercises silently — the position pair (long shares + short call) is reconciled in the books, but no `OPASN` / `OPEXP` / `OPTRD` activity is logged and no equity event appears in `/v2/account/portfolio/history`. This was discovered while investigating AMD's reported −$17,319 total P&L (FC-018 scorecard).

Specific case: contract `AMD260116C00212500` (sold 2026-01-14 at $8.60, expired 2026-01-16 with AMD at $231.79 = $19.29 ITM) was auto-exercised by the holder but produced no record. The order remains frozen at `status="filled"` with no lifecycle event. Investigation reproducer scripts at `/tmp/amd_*.py`; full reconciliation at `amd_reconciliation.md` in the project root.

A daily-P&L hypothesis fit test confirmed:

| Hypothesis | Σ residual gap |
|---|---:|
| Trust ledger as-is (200 shares Feb–Apr) | −$5,206 (off by ~100 × AMD drift) |
| **+ silent 2026-01-16 exercise (−100)** | **+$4,476 (best fit)** |
| + a second silent loss | +$15,620 (over-corrects) |

Hypothesis B wins decisively. The account behaved as if it held 100 shares (not 200) from 1/31 → 4/18, which means the missing 1/16 record explains the entire discrepancy. No second silent event occurred.

## Goals

- Inject the missing `OPASN` + `OPTRD` pair as synthetic rows so the FC-018 scorecard, cycle view, and ACB walk show the correct AMD per-symbol attribution.
- Establish a reusable pattern (`activity_id` prefix + audit query) for future silent-settlement corrections.
- Preserve the headline `Total Return = NLV − sum(deposits)` invariant — it is sourced independently from Alpaca and reflects reality regardless of per-symbol synthetic adjustments.

## Non-goals

- Building a corrections-table layer with overlay views — overkill for a single fix. Graduate to that pattern only if a second correction is ever needed.
- Fixing the upstream Alpaca paper-engine bug — out of our control. A support ticket has been filed with order id `14255807-d0b8-4f0e-8614-3bc92d83cef0`.
- Auto-detecting silent settlements going forward (separate FC if this recurs).

## Proposed approach

Insert two rows directly into `options_wheel.trades_from_activities`:

| activity_id | activity_type | symbol | underlying | qty | price | net_amount | transaction_time |
|---|---|---|---|---:|---:|---:|---|
| `synthetic-fc-021-amd-2026-01-16-opasn` | `OPASN` | `AMD260116C00212500` | `AMD` | 1 | NULL | 0 | 2026-01-17 00:00 UTC |
| `synthetic-fc-021-amd-2026-01-16-optrd` | `OPTRD` | `AMD` | `AMD` | −100 | 212.50 | +21,250 | 2026-01-17 00:00 UTC |

The `synthetic-fc-021-` prefix makes the rows trivially identifiable. Add to a runbook section how to filter / remove them.

The activities ingestor is idempotent on `activity_id` and only inserts records returned by Alpaca — it will never overwrite or duplicate the synthetic rows. If Alpaca later emits the real records, they'll arrive with their own activity_ids, the duplicates can be detected, and the synthetic rows can be deleted.

## Critical files

- `options_wheel.trades_from_activities` (BQ table) — synthetic rows inserted
- No code changes — the existing FC-018 / FC-019 view stack picks up the correction automatically because every downstream view sums or windows over `trades_from_activities`.

## Reuse

- `dashboard/backend/services/bigquery.py` view definitions are unchanged
- `wheel_cycles_from_activities` view picks up the synthetic OPTRD via its existing `cycle_share_cash` CTE window-join
- `fc018_per_symbol_scorecard` view recomputes `share_side_pnl` and `total_realized_pnl` from raw OPTRD net cash flow

## Risks & mitigations

- **Risk:** Synthetic data contaminates the canonical raw table. *Mitigation:* `synthetic-fc-021-` prefix on `activity_id`. Audit query: `SELECT * FROM trades_from_activities WHERE activity_id LIKE 'synthetic-%'` returns exactly the synthetic rows. Removal: `DELETE FROM trades_from_activities WHERE activity_id LIKE 'synthetic-fc-021-%'`.
- **Risk:** Per-symbol total summed across the scorecard no longer approximates the headline Total Return. *Accepted:* The headline is sourced from NLV − deposits (Alpaca truth), and the per-symbol view's job is to attribute reality to the correct symbol — not to sum-equal the headline. After the fix, per-symbol sum is ~$44.9k vs headline ~$20.1k; the divergence reflects the silent settlement which Alpaca already absorbed at the account level.
- **Risk:** A future re-ingest from scratch loses the corrections. *Mitigation:* This SQL INSERT is captured in the `## Execution` section below; it can be re-run idempotently (the `activity_id` is unique-keyed via the table's REQUIRED constraint, so a duplicate insert errors cleanly).

## Rollout

1. Insert the two synthetic rows via `bq query` (single transaction).
2. Verify `fc018_per_symbol_scorecard` for `AMD` shows `share_side_pnl ≈ −$3,000` and `total_realized_pnl ≈ +$5,309`.
3. Verify `wheel_cycles_from_activities` for AMD shows three cycles with `cap_gain` of −$3,750 / $0 / +$750 (Cycle 2 now correctly identifies `AMD260116C00212500` as the terminating call).
4. Hit the live dashboard `/api/v2/scorecard?days=365` to confirm propagation.

Rollback: `DELETE FROM options_wheel.trades_from_activities WHERE activity_id LIKE 'synthetic-fc-021-%'`.
