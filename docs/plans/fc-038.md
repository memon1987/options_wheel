## What revision 2 changed

Revision 1 was structured as an *extensibility* project: five mechanical seams in
Phase 1, and a one-paragraph Phase 2 that assumed `CallSeller` / `CallRoller` /
`ExecutionEngine` were reusable with a single swapped cost-basis provider. Both
reviewers independently rejected that framing. The risk is concentrated in
Phase 2, and the load-bearing reuse claim was false.

Four things changed materially:

1. **A shared-state channel was missed entirely.** The GCS opportunity store is
   not strategy-keyed, so two services would read each other's scan output and
   place orders in the wrong brokerage account. This falsified the plan's central
   rollback claim. It is now Phase 1 seam #1 and gates everything.
2. **Phase 1 seam #3 was dead work.** Wheel state persistence has never
   functioned in production (see FC-039). There is nothing to migrate, and the
   "legacy shim + copy script" mitigation protected against a scenario that
   cannot occur.
3. **The "~70% reusable, one wheel assumption" claim was wrong.** There are at
   least four wheel assumptions in `call_seller.py` alone. Phase 2 is now written
   as a *policy* design, not a plumbing exercise.
4. **The reuse-vs-fork decision was never actually argued.** Revision 1 assumed
   seam injection into live wheel classes. Alternatives are now recorded with
   reasoning — see "Design alternatives considered".

## Context

We want to run a second strategy — a standalone covered-call strategy (buy/hold
stock, sell calls against it) — alongside the existing options wheel, reusing as
much of the engine as possible. Two questions drove this plan:

1. **Isolation:** separate Alpaca accounts per strategy, or one shared account
   with tagged positions?
2. **Reuse:** which components transplant as-is, which need refactoring, and what
   should a strategy-extensibility seam look like?

This plan is the output of a codebase architecture audit, market research on
Alpaca account mechanics and how multi-strategy frameworks (QuantConnect/LEAN,
NautilusTrader, Lumibot) handle strategy isolation, Phase 0 empirical
verification against the live Alpaca API, and a two-reviewer adversarial pass.

## Recommendation (TL;DR)

**Separate Alpaca account per strategy. Do not attempt position tagging.** Deploy
the covered-call strategy as a second Cloud Run service built from the *same*
container image, pointed at its own paper account, its own config YAML, its own
GCS state, and its own BigQuery dataset.

Reuse is real but narrower than revision 1 claimed. The *mechanics* transplant
(chain selection, order submission, share accounting); the *policies* do not
(cost basis, drawdown response, sizing basis, earnings gating). Phase 1 extracts
the seams; Phase 2 writes covered-call policy explicitly rather than inheriting
wheel policy by default.

### Why not position tagging (stress-tested)

Tagging was evaluated seriously and fails on four independent grounds. All four
were re-verified against code during review.

1. **Alpaca has no position tags.** Positions are netted per symbol per account —
   one row per symbol, one blended `avg_entry_price`, no lots, no sub-books, no
   metadata. Only *orders* can carry attribution (`client_order_id`, ≤48 chars,
   unique). If both strategies hold the same underlying, the broker cannot
   distinguish them, and a sell from one strategy silently closes the other's
   shares.
2. **Option assignment breaks attribution.** Assignments/exercises/expirations
   arrive as non-trade activities (`OPASN`/`OPTRD`) with **no client_order_id**.
   A wheel post-assignment (long shares + short call) is *literally the same
   book* as a covered-call position. The only attribution key is the OCC contract
   symbol — which requires a persistent internal ledger plus a hard "one
   option-writing strategy per underlying" rule anyway.
3. **Our own engine actively adopts foreign positions.** `WheelEngine.reconcile_positions()`
   fetches *all* account positions and adds any untracked position into wheel
   state ("Position exists in Alpaca but not in wheel state — adding",
   `src/strategy/wheel_engine.py:1262`). It infers assignments by position-diffing
   (puts↓ + shares↑, calls↓ + shares↓). A covered-call strategy's shares would be
   adopted by the wheel, which would then **sell calls against shares it doesn't
   own the thesis for**, and misfire `wheel_cycle_completed` analytics when the
   other strategy's calls are assigned. Both reviewers called this decisive on its
   own.
4. **Risk sizing is account-wide.** `position_sizing.py` sizes against
   whole-account `portfolio_value`/`buying_power`; `wheel_engine._can_open_new_positions`
   counts all account positions. Two strategies sharing an account would each size
   as if they owned all the capital — double-allocating buying power — unless we
   build per-strategy capital budgets, which Alpaca will not enforce for us.

Industry practice agrees: QuantConnect refuses to support two algorithms on one
brokerage account; NautilusTrader and Lumibot support it only via full
virtual-ledger layers that still have the assignment-attribution blind spot.
Building that ledger is a multi-week project that buys us nothing over a second
account.

### The one-live-account constraint (important caveat)

Alpaca retail allows **one live brokerage account per person** but **up to 3
paper accounts** (creatable from the dashboard; each has its own API keys). We
currently run paper (`ALPACA_PAPER_TRADING=true`, `cloudbuild.yaml:75`), so a
second paper account is available today at zero cost — and Phase 0 confirmed it.

If/when we go live with both strategies, the options are: (a) separate legal
entities (IRA/LLC/spouse — verify API access with Alpaca support), (b) a
different broker for one strategy, or (c) consolidate into one live account
behind a **disjoint symbol universe rule** plus per-strategy capital budgets.

**Consistency note from review:** revision 1 dropped the disjoint-universe guard
because consolidation is hypothetical, while keeping the strategy-prefixed
`client_order_id` *for* consolidation — at the cost of rotating a live
idempotency key on the money-making wheel. Same hypothetical, opposite reasoning.
Revision 2 resolves this: **both are treated as consolidation-only.** The guard
stays dropped, and the `client_order_id` prefix no longer applies to the wheel
(see Phase 1 seam #4). If consolidation ever becomes real, both get built then.

## Goals

- Covered-call strategy runs in its own Alpaca (paper) account, own Cloud Run
  service, own state, own analytics — zero interference with the wheel.
- Shared code stays shared: one repo, one image, strategy selected by config.
  No fork.
- Covered-call *policy* is stated explicitly, not inherited by default from
  wheel policy.
- Extensibility seams so a third strategy is incremental, not another project.
- A covered-call backtest that replays the production covered-call engine through
  the FC-032 simulator (see Phase 4 for why this depends on Phase 2, not on a
  backtester interface).

## Non-goals

- Shared-account position tagging / virtual portfolio ledger (rejected above).
- Live-account entity structuring (deferred; see Open questions).
- Dashboard multi-strategy UI (Phase 5, separate FC).
- Merging wheel and covered-call into one engine per ticker.
- Changes to wheel strategy *behavior*. Phase 1 touches wheel code paths but must
  not change what the wheel does — see the golden-file gate in Verification.

### Phase 1 — Isolation seams

**Framing change from revision 1.** Do not enumerate the seams we happen to
notice. Enumerate *every piece of process-global or externally-shared state* and
prove each is either strategy-keyed or strategy-agnostic. Start from:

```
grep -rn "options_wheel\|wheel_state\|opportunities/\|Config()" src/ deploy/
```

That sweep is what surfaced seam #1, which revision 1 missed while listing the
opportunity store under "Reuse."

**1. Strategy-key the GCS opportunity store — BLOCKING, do this first.**
`src/data/opportunity_store.py:18` hardcodes `bucket_name="options-wheel-opportunities"`;
`_get_blob_path` (`:329-340`) returns `opportunities/{YYYY-MM-DD}/{HH-MM}.json`
with no strategy scoping. Both call sites (`deploy/cloud_run_server.py:182`
writes in `/scan`, `:308` reads in `/run`) pass only `config`.

Two services from the same image share these blob keys. The covered-call
service's `/run` would read the **wheel's** scan output and execute wheel
cash-secured puts in the covered-call account against $4M of margin buying power
— and vice versa. Orders placed in the wrong account cannot be unwound by
deleting a service, which falsifies revision 1's rollback story.

Fix: `opportunities/{strategy_id}/{date}/{time}.json`, plus a per-strategy bucket
name from config. **No second service may deploy before this lands.**

**2. Single config accessor + account-number interlock.**
`deploy/cloud_run_server.py` has **17 bare `Config()` calls** (verified by
`grep -c`). `Config.__init__` defaults to `config/settings.yaml` (`config.py:46`)
and resolves credentials to the *wheel's* keys. Same image, both services: any
endpoint whose `Config()` is not converted silently authenticates as the wheel
and acts on it.

Account isolation — this plan's entire thesis — cannot rest on 17 correct
hand-edits with no check. Fix:
- One module-level `get_config()` resolving `STRATEGY_CONFIG` once per process.
- **A startup assertion** that `AlpacaClient.get_account().account_number` equals
  an `expected_account_number` pinned in the YAML (`PA3D36DVXSZ2` for the wheel,
  `PA37XLNWDLB3` for covered calls — both captured in Phase 0). Refuse to serve
  on mismatch. Phase 0's account numbers become a safety interlock, not a table
  in a document.

**3. Config namespacing** (`src/utils/config.py`): add a top-level `strategy_id`;
make `_validate_config` schema-aware per strategy type instead of hardcoding
`required_sections = ['alpaca','strategy','risk','stocks','monitoring']`
(`:109-114`). Note `stocks.symbols` is currently required and non-empty
(`:209-212`) but the covered-call universe derives from holdings — it must become
optional for that profile, or the service crashes on boot.

**Credential indirection must remain env-var based.** `_load_secret`
(`config.py:33`) reads `GOOGLE_CLOUD_PROJECT` / `GCP_PROJECT_ID`; Cloud Run sets
neither — `cloudbuild.yaml:75` sets `GCP_PROJECT`, a third name. The Secret
Manager fallback path has therefore **never executed in production**; it works
only because `--set-secrets` injects values as env vars and `_load_secret`
short-circuits (`config.py:27-29`). If this seam is implemented as runtime Secret
Manager calls it returns `""` and `_validate_config:126-129` crashes the service
on boot. The seam is only about *which env var names* the YAML references. Fix
the `GCP_PROJECT` naming mismatch while in here, and the wrong error message at
`:126` (says `ALPACA_API_KEY_ID`; the map keys on `ALPACA_API_KEY`).

**4. Strategy-prefixed client_order_id — wheel-neutral.**
`_generate_client_order_id` (`src/api/alpaca_client.py:117-125`) is a module-level
function with exactly **one** call site (`:523` — revision 1 said "every call
site"; there is one). It returns `hexdigest()[:32]`.

**Revised approach after review.** Revision 1 called the current scheme's
behavior "a latent collision." It is not — it is the deterministic idempotency
the docstring at `:118-123` explicitly promises, and Alpaca rejecting the
duplicate is the feature working. Idempotency is entirely broker-side: there is
no local order registry, so revision 1's mitigation ("have retry lookup check
both formats for one day") describes **code that does not exist**.

On a mid-day deploy, a retry of an order already accepted under `abc123…` would
hash to `wheel-abc123…`, Alpaca would see a new id, and **fill a second
contract**. With 6 `/run` and 6 `/scan` schedules during market hours and a
confirmed duplicate-order history (FC-009), that is not theoretical.

Fix: **emit the unprefixed id for `strategy_id == "wheel"` permanently**; prefix
only new strategies. Zero deploy-boundary risk, and the wheel's live idempotency
key never rotates.

**5. CostBasisProvider abstraction** (`src/strategy/call_seller.py:429`, called
from `:71` and `:235`): extract behind an injected provider —
`WheelCostBasisProvider` (wheel state → BQ OPASN put-strike lookup → Alpaca
fallback) vs `StockEntryCostBasisProvider` (Alpaca `avg_entry_price`, correct for
purchased shares; the known `cost_basis=0` bug affects only assignment-acquired
stock).

**Sequenced after FC-039, which is now decided: delete the dead path.** Source #1
of the wheel chain never resolves in production because state persistence is
dead, and the owner's call is to remove it rather than wire it up. So
`WheelCostBasisProvider` is a **two**-source chain — BQ OPASN put-strike lookup,
then Alpaca fallback — not three. Build the provider against that reality; do not
port a wheel_state branch that has never executed.

The state-hook portion is largely already done: `CallSeller.__init__` takes
`wheel_state_manager=None` (`:20`) and `handle_call_assignment` takes it
optionally (`:840`). Take the BQ client as an injected dependency too, which also
keeps the hermeticity property that `conftest.py`'s `_no_production_bigquery`
fixture currently enforces by monkeypatching — injection is the more durable
version of the same guarantee.

**6. Parameterized analytics dataset** — wider than revision 1 scoped. Five
classes default to `options_wheel`: `trade_journal.py:68`, `analytics_writer.py:128`,
`activities_ingestor.py:92`, `portfolio_history_ingestor.py:66`,
`stock_history_ingestor.py:75`. Revision 1 named only the first two.
`activities_ingestor` matters most — it ingests OPASN/OPTRD, i.e. **every
assignment and call-away in the covered-call book**, and revision 1's verification
checklist tested it while never scoping it. Also fix the hardcoded dataset in the
SQL string at `call_seller.py:522`. Add a `strategy_id` column on new rows
(nullable, backfill-free).

~~7. **Parameterized state storage**~~ **Dropped — was dead work.** Revision 1
specified `_STATE_BLOB_PATH` → `f"{strategy_id}/current_state.json"` plus a
legacy-path shim and a one-time copy script. There is nothing to migrate: wheel
state has never persisted (FC-039). Whatever FC-039 decides — enable persistence
or delete the path — the covered-call strategy inherits that decision. If FC-039
enables persistence, that is a **behavior change to the live wheel** (cost-basis
floors would begin resolving from source #1 and change which strikes are
sellable), and it needs its own canary, not a path rename inside this plan.

~~8. **Disjoint symbol universe guard**~~ **Dropped 2026-07-18 (owner decision).**
With the books in physically separate accounts (`PA37XLNWDLB3` vs `PA3D36DVXSZ2`,
verified in Phase 0), symbol overlap is harmless — Alpaca cannot confuse a share
in one account for a share in another — and a hard block would halt the bot
whenever a manually-bought holding matched one of the wheel's 14 symbols. The
guard is meaningful only under single-account consolidation.

**Review caveat, accepted:** the guard was also the only mechanism that ever
inspected *what the covered-call book is allowed to touch*. Dropping it leaves
that hole. Phase 2 fills it with an inventory **validator** (optionability,
liquidity, spread width) rather than a cross-strategy collision check — a
different control for a different purpose.

### Phase 2 — Covered-call engine

New `src/strategy/covered_call_engine.py` + `src/strategy/covered_call_state_manager.py`.

**Stock entry is manual**: long positions are bought by hand via the Alpaca UI in
the dedicated account; the bot automates only call selling, early-close, rolling,
and assignment handling. Reconciliation *adopts* every equity position it finds —
safe precisely because the account is dedicated, and it means manually
added/trimmed lots are picked up next cycle with no config change.

Revision 1 stopped here. Review found six wheel policies that are silently wrong
for a covered-call book. Each must be decided explicitly:

| Wheel policy | Why it is wrong here | Decision |
|---|---|---|
| Cost basis = assigning put strike | Basis is a purchase price the operator chose | `StockEntryCostBasisProvider` (Alpaca `avg_entry_price`) |
| Strike floor | — | **Hard floor: `strike >= avg_entry_price`** (owner decision 2026-07-18) |
| Drawdown ≥5% → pause writing calls | Redundant once a hard basis floor is in force — the floor already prevents a loss-forcing assignment | **Disabled** for this profile (owner decision 2026-07-18) |
| Sizing from *owned* shares | Inventory grows by hand; incremental lots must get covered | **See "Sizing" below** |
| No earnings gate on *opening* | Wheel's 14 symbols are vetted; this book's are not | Wire `EarningsCalendarService` into the open path |
| Dividends ignorable (low-yield tech universe) | A discretionary book is exactly where dividend payers land | **See "Ex-dividend" below** |
| 14 vetted symbols | No universe, no criteria | Inventory validator (below) |

**Drawdown and strike-floor policy — DECIDED 2026-07-18 (owner).**

**Hard floor: `strike >= avg_entry_price`.** Never write a call that could force
a loss on the shares. This mirrors wheel discipline exactly and is the simplest
rule to reason about and to explain after the fact.

A net floor (`strike + premium >= avg_entry_price`) was considered and rejected.
It is arguably the more economically precise line — it refuses only assignments
that lose money net of premium — but it accepts realizing stock losses in
exchange for premium, and the owner's preference is that this book never does
that.

**Consequence, stated plainly: idle inventory is now the strategy's primary
failure mode, not an edge case.** Any lot whose blended `avg_entry_price` sits
above current strikes stops generating premium entirely until the underlying
recovers past basis. A DCA'd position bought into strength, or any name in a
correction, goes quiet. This is a deliberate trade — capital preservation over
premium capture — but it must be *visible*, or the book will look broken when it
is merely being disciplined. See the observability requirement in Risks.

**The FC-029 drawdown pause is disabled for this profile.**
`call_drawdown_pause_threshold` defaults to `0.05` (`config.py:283`,
`call_seller.py:123-134`) and makes `evaluate_covered_call_opportunity` return
`None` on any name down >5% from basis. Given the hard floor, it protects nothing
the floor does not already protect — a strike at or above basis cannot produce a
losing assignment regardless of where the stock trades — while blocking far-OTM
above-basis calls that would otherwise clear `min_call_premium`. It is therefore
redundant-but-restrictive and is set to disabled in `config/covered_call.yaml`.

Both settings are explicit in the covered-call config, never inherited from
`config/settings.yaml`. A config-validation assertion should fail loudly if
either is absent, so a future default change to the wheel cannot silently alter
covered-call behavior.

**Sizing.** Revision 1 claimed `ExecutionEngine` "already computes committed-share
accounting" and that Phase 2 would "sell up to `floor(uncommitted_shares/100)`."
It does not size. `_calculate_call_position` (`call_seller.py:215`) computes
`max_contracts = shares_owned // 100` from **owned** shares;
`ExecutionEngine:339-359` then compares against available and **rejects the whole
opportunity** — binary, no partial fill.

The modal covered-call workflow breaks on this: hold 300 shares with 3 calls
open, buy 100 more → seller proposes 4 → guard sees `available=100 < 400` →
blocked → **the incremental lot is never covered, and this repeats forever**.
Sizing must move into the seller and be computed from uncommitted shares. Depends
on FC-041 (the guard's parser must be correct first).

**Ex-dividend / early exercise.** `grep -rni "dividend|ex-div|CDIV" src/`
(excluding `backtesting/`) returns **zero hits** — production is blind to it,
while the backtest broker models it (`broker.py:299` `assign_call_early(reason="ex_dividend")`,
`:308` `credit_dividend`). The simulator will therefore model a risk production
does not have code for. Early assignment the day before ex-dividend, when a short
call's extrinsic value falls below the dividend, is the classic covered-call
blowup — and far likelier here than in the wheel's low-yield mega-cap universe.
Minimum viable: skip or roll short calls whose extrinsic value is below the
upcoming dividend within N days of ex-date. If we decline to build it, the plan
must state in writing that this account holds no dividend payers.

**Inventory validator (replaces the dropped universe guard).** Before writing a
call on an adopted holding, validate: the underlying is optionable; the chain has
acceptable liquidity and spread width; earnings are not within the DTE window.
Reject-and-log rather than trade. This is the input validation the wheel gets for
free from a curated list.

**Operator opt-out.** Blanket adoption gives the operator discretion over what
they *own* but none over what gets *written against*. A long-term hold gets
called away; a large unrealized gain gets called away, forcing an unauthorized
taxable event. Add an `excluded_symbols` list in `config/covered_call.yaml`, and
write the invariant into the operator runbook: *this account holds nothing you
are unwilling to have called away.*

**Rolling.** `CallRoller` requires the full active-call-detail and roll-count
surface (8 `wheel_state` call sites, two of them decision gates). The "simple
state: HOLDING_STOCK → SELLING_CALLS" state manager of revision 1 cannot support
it. Either scope `covered_call_state_manager.py` to that full surface, or **drop
rolling from Phase 2** and add it in a follow-up. Recommendation: drop it from
Phase 2 — early-close plus re-write next cycle covers most of the value, and it
removes the largest single chunk of Phase 2 scope. Related hazard: nothing stops
the operator selling a call manually in the UI, in which case
`get_active_call_details` returns nothing for a live short call.

**4x margin.** The mitigation in revision 1 ("size against `equity` not
`buying_power`, assert in config validation") targets the wrong code — see Risks.

### Phase 3 — Deployment

Second Cloud Run service `covered-call-strategy` in `cloudbuild.yaml` from the
same image: `STRATEGY_CONFIG=config/covered_call.yaml`, secrets
`alpaca-api-key-cc`/`alpaca-secret-key-cc`, own state prefix, dataset
`covered_call`. `--max-instances=1` same as wheel (verified live:
`autoscaling.knative.dev/maxScale: "1"`).

**BigQuery provisioning and IAM — new in revision 2.** The runtime SA
`799970961417-compute@developer.gserviceaccount.com` has `bigquery.dataViewer` +
`bigquery.jobUser` but **no `dataEditor`** and no project Editor. Writes to
`options_wheel` work only because of a *dataset-level* WRITER grant. A new
`covered_call` dataset gets no such grant, and the SA cannot `datasets.create` —
so `create_dataset(exists_ok=True)` returns 403 and the first analytics write
raises. The service would trade fine against Alpaca while silently losing all

## Design alternatives considered

Recorded per review: revision 1 asserted an approach without arguing against the
alternatives. None of these are chosen, but each is now on the record with why.

**A. Separate `CoveredCallSeller` / `CoveredCallConfig` classes instead of
injecting seams into the live wheel's `CallSeller` / `Config`.**
Given six divergent policies (table above), two classes sharing a small sizing
helper may be *less* total code than one class with six injected policy knobs —
and it would leave the live wheel's code paths literally untouched, driving this
plan's #1 stated risk to approximately zero. `Config` in particular is ~600 lines
of wheel vocabulary (`put_target_dte`, `put_delta_range`, `rolling_*`), and making
`_validate_config` schema-aware bolts a second schema onto a wheel-shaped class.
**Rejected because:** it forfeits the shared-improvement property — a future fix
to chain selection or share accounting would have to be made twice, which is the
drift this plan exists to prevent. **But this is the closest call in the plan**,
and if Phase 1 turns out to require more than ~5 policy injection points into
`CallSeller`, revisit it. The "fork-in-disguise" risk cited in revision 1 applies
to *services*, not to two sellers in one tree — that was a category error.

**B. One service, two configs, routed by request (`?strategy=covered_call`).**
Avoids a second Cloud Run service and 20 cloned schedulers. **Rejected because:**
shared process memory, no independent scale or rollback, and one bad deploy takes
down both books. Worth recording that this design makes the shared-state problem
*unavoidable to notice*, which the chosen design did not — seam #1 was missed
precisely because separate services created an illusion of isolation.

**C. A per-symbol opt-in file instead of blanket adoption.**
The middle ground between "configured universe" and "adopt everything."
**Partially adopted:** rejected as the primary mechanism (it reintroduces the
config-maintenance burden manual entry was meant to avoid), but the
`excluded_symbols` opt-*out* in Phase 2 captures most of the safety value at a
fraction of the friction.

**D. Read-only shadow mode as a phase gate.**
A phase where the covered-call engine observes a hand-managed book and logs what
it *would* have done, before any order is submitted. **Adopted** — folded into
the Rollout as the first covered-call step, replacing revision 1's straight jump
to dry-run. It is the cheapest way to surface policy mismatches.

**E. Defer Phase 1's live-wheel refactor until Phase 2 is proven.**
Phase 1's only consumer is Phase 2; building Phase 2 against a hardcoded second
config first, then extracting only the seams that turned out to be needed, avoids
touching production wheel code for a strategy that may change shape.
**Rejected because:** seams #1 and #2 are safety-critical and must exist before
*any* second service runs, so Phase 1 cannot be wholly deferred. Seams #5 and #6
could be, and that ordering is preserved inside the Rollout.

## Risks & mitigations

- **Risk:** refactors regress the live wheel.
  - Mitigation: golden-file config test (below); wheel `client_order_id` never changes format; canary deploy; hermetic suite green (already enforced by `conftest.py` on `main`).
- ~~**Risk:** client_order_id format change breaks idempotency~~ **Retired** — the wheel keeps its unprefixed id permanently (seam #4), so there is no deploy boundary to cross.
- ~~**Risk:** state-blob path migration loses wheel state~~ **Retired** — there is no persisted state to lose (FC-039). Replaced by: *if FC-039 enables persistence, that is a behavior change requiring its own canary.*
- **Risk:** the two services drift (fork-in-disguise).
  - Mitigation: one image, one `src/` tree, config-only divergence; CI builds a single artifact.
- ~~**Risk:** Alpaca paper-account facts wrong~~ **Retired 2026-07-18** — Phase 0 verified empirically.
- **Risk:** the covered-call account is 4x margin (`multiplier: 4`, $1M equity → $4M buying power) vs the wheel's 2x.
  - **Mitigation corrected in revision 2.** Revision 1 said "size against `equity` not `buying_power`; assert in config validation." Wrong target: `position_sizing.py` reads `buying_power` unconditionally (`:38-39`, `:63`, `:396-399`) — there is no knob to assert on — and it sizes *puts*; covered-call contract count comes from shares and never touches it. The real exposure is that the **operator** can buy $4M of stock on $1M of equity in the UI, and the bot writes calls against a leveraged book it has no drawdown model for. Actual mitigation: set `max_portfolio_allocation` against equity in the covered-call config, and add a monitor alert on `long_market_value > equity`.
- **Risk:** manual stock entry races the bot (shares sold manually out from under a short call → naked call).
  - Mitigation: recompute uncommitted shares from live positions every cycle (requires FC-041's parser fix); runbook rule "never manually sell shares while short calls are open — buy-to-close first"; monitor alert on `short_calls × 100 > shares`.
- **Risk (elevated in revision 2 — now the primary failure mode):** with the hard basis floor, any lot whose blended `avg_entry_price` sits above current strikes generates **no premium at all** until the underlying recovers past basis. A DCA'd position bought into strength, or any name in a correction, goes silently quiet. This is an accepted consequence of the owner's floor choice, not a defect — but undetected it looks identical to the bot being broken.
  - Mitigation: this needs real observability, not a log line. (a) Emit a structured `skipped: strike_floor_above_market` decision per symbol per cycle, carrying `avg_entry_price`, best available strike, and the gap. (b) Surface an `idle_inventory_count` / `idle_market_value` metric so idle capital is a number on a dashboard, not an inference from absent trades. (c) Alert if a holding is idle for more than N consecutive sessions — that is the operator's signal to reconsider the lot, which is a decision only they can make. Mirrors the FC-030 drawdown-pause alerting pattern.
- **Risk:** covered-call analytics silently lost to BigQuery 403s.
  - Mitigation: explicit dataset + IAM provisioning step in Phase 3, verified with a test insert before the service takes traffic.
