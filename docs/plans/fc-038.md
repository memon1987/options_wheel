## Context

We want to run a second strategy — a standalone covered-call strategy (buy/hold stock, sell calls against it) — alongside the existing options wheel, reusing as much of the engine as possible. Two questions drove this plan:

1. **Isolation:** separate Alpaca accounts per strategy, or one shared account with tagged positions?
2. **Reuse:** which components transplant as-is, which need refactoring, and what should a strategy-extensibility seam look like?

This plan is the output of a codebase architecture audit plus market research on Alpaca account mechanics and how multi-strategy frameworks (QuantConnect/LEAN, NautilusTrader, Lumibot) handle strategy isolation.

## Recommendation (TL;DR)

**Separate Alpaca account per strategy. Do not attempt position tagging.** Deploy the covered-call strategy as a second Cloud Run service built from the *same* container image, pointed at its own paper account, its own config YAML, its own GCS state blob, and its own BigQuery dataset. Extract a small number of seams (cost-basis provider, config namespacing, client-order-id prefix, storage paths) so ~70% of the existing engine is reused rather than forked.

### Why not position tagging (stress-tested)

Tagging was evaluated seriously and fails on four independent grounds:

1. **Alpaca has no position tags.** Positions are netted per symbol per account — one row per symbol, one blended `avg_entry_price`, no lots, no sub-books, no metadata. Only *orders* can carry attribution (`client_order_id`, ≤48 chars, unique). If both strategies hold the same underlying, the broker cannot distinguish them, and a sell from one strategy silently closes the other's shares.
2. **Option assignment breaks attribution.** Assignments/exercises/expirations arrive as non-trade activities (`OPASN`/`OPTRD`) with **no client_order_id**. A wheel post-assignment (long shares + short call) is *literally the same book* as a covered-call position. The only attribution key is the OCC contract symbol — which requires a persistent internal ledger plus a hard "one option-writing strategy per underlying" rule anyway.
3. **Our own engine actively adopts foreign positions.** `WheelEngine.reconcile_positions()` fetches *all* account positions and adds any untracked position into wheel state ("Position exists in Alpaca but not in wheel state — adding", `src/strategy/wheel_engine.py:1267`). It infers assignments by position-diffing (puts↓ + shares↑, calls↓ + shares↓). A covered-call strategy's shares would be adopted by the wheel, which would then **sell calls against shares it doesn't own the thesis for**, and misfire `wheel_cycle_completed` analytics when the other strategy's calls are assigned.
4. **Risk sizing is account-wide.** `position_sizing.py` sizes against whole-account `portfolio_value`/`buying_power`; `wheel_engine._can_open_new_positions` counts all account positions. Two strategies sharing an account would each size as if they owned all the capital — double-allocating buying power — unless we build per-strategy capital budgets, which Alpaca will not enforce for us.

Industry practice agrees: QuantConnect refuses to support two algorithms on one brokerage account; NautilusTrader and Lumibot support it only via full virtual-ledger layers that still have the assignment-attribution blind spot. Building that ledger is a multi-week project that buys us nothing over a second account.

### The one-live-account constraint (important caveat)

Alpaca retail allows **one live brokerage account per person** but **up to 3 paper accounts** (creatable from the dashboard; each has its own API keys). We currently run paper (`ALPACA_PAPER_TRADING=true`, `cloudbuild.yaml:75`), so a second paper account is available today at zero cost.

If/when we go live with both strategies, the options are: (a) separate legal entities (IRA/LLC/spouse — verify API access with Alpaca support), (b) a different broker for one strategy, or (c) consolidate into one live account behind a **disjoint symbol universe rule** (each underlying is owned by exactly one strategy) plus per-strategy capital budgets. Strategy-prefixed `client_order_id` is baked in from day one to keep (c) viable. The disjoint-universe *guard* was dropped (owner decision 2026-07-18) — see Phase 1 — so option (c) would require building it at that time.

## Goals

- Covered-call strategy runs in its own Alpaca (paper) account, own Cloud Run service, own state, own analytics — zero interference with the wheel.
- Shared code stays shared: one repo, one image, strategy selected by config. No fork.
- Extensibility seams (config namespacing, cost-basis provider, state paths, dataset naming, order-id prefixes) so a third strategy is incremental, not another project.
- A covered-call backtest that replays the production covered-call engine through the FC-032 simulator, reusing its data layer and broker (see Phase 4 for why this depends on Phase 2, not on a backtester interface).

## Non-goals

- Shared-account position tagging / virtual portfolio ledger (rejected above).
- Live-account entity structuring (decision deferred until live go-live; see Open questions).
- Dashboard multi-strategy UI (Phase 5, separate FC — dashboard/BQ views assume the `options_wheel` dataset throughout).
- Merging wheel and covered-call into one engine per ticker (they stay separate strategies in separate accounts).
- Changes to wheel strategy behavior. The wheel keeps running unmodified throughout.

## Proposed approach

One repo, one container image, N Cloud Run services. Each service gets `STRATEGY_CONFIG` (path to its YAML), its own Secret Manager credentials, its own `STATE_STORAGE_BUCKET`/blob path, and its own BigQuery dataset. Reuse boundaries below.

### Phase 1 — Extensibility seams (no behavior change to the wheel)

1. **Config namespacing** (`src/utils/config.py`): add a top-level `strategy_id` key; make `_validate_config` schema-aware per strategy type instead of hardcoding wheel sections (`:115`); let the `alpaca:` block name its Secret Manager secret IDs / env vars (e.g. `ALPACA_API_KEY_CC`) instead of the fixed `_SECRET_MANAGER_MAP` (`:82`). Existing `config/settings.yaml` remains valid unchanged.
2. **Strategy-prefixed client_order_id** (`src/api/alpaca_client.py:117`): `_generate_client_order_id` → `{strategy_id[:6]}-{hash[:32]}` = 39 chars, under Alpaca's 48 limit, still deterministic/idempotent. (Original spec said `hash[:25]`; the function already returns `hexdigest()[:32]` and prefixing still fits, so there is no reason to shed entropy.) Note it is a **module-level function**, not a method — threading `strategy_id` through means a signature change at every call site. Also fixes a latent collision: today two processes submitting the same symbol/qty/side/price on the same day collide on the same id.
3. **Parameterized state storage** (`src/strategy/wheel_state_manager.py:14`): `_STATE_BLOB_PATH` → `f"{strategy_id}/current_state.json"`, with a migration shim that reads the legacy `wheel_state/current_state.json` path for `strategy_id == "wheel"`.
4. **Parameterized analytics dataset** (`src/data/trade_journal.py`, `analytics_writer.py`): **smaller than originally scoped** — both classes *already* accept `dataset_id: str = "options_wheel"` as a constructor parameter (`trade_journal.py:68`, `analytics_writer.py:128`). Nothing is hardcoded. The work is threading the config value through at the call sites, plus a `strategy_id` column on new rows (nullable, backfill-free).
5. **CostBasisProvider abstraction** (`src/strategy/call_seller.py:429`): extract `_resolve_cost_basis_floor` behind an injected provider — `WheelCostBasisProvider` (current chain: wheel state → BQ OPASN put-strike lookup → Alpaca fallback) vs `StockEntryCostBasisProvider` (Alpaca `avg_entry_price`, which is correct for purchased shares — the known `cost_basis=0` bug applies only to assignment-acquired shares). The state-hook portion is **mostly already done**: `CallSeller.__init__` already takes `wheel_state_manager=None` (`:20`) and `handle_call_assignment` already takes it optionally (`:840`). Remaining work is the provider extraction itself (`:429`, called from `:71` and `:235`).
~~6. **Disjoint symbol universe guard**~~ **Dropped 2026-07-18 (owner decision).** The guard would hard-block the bot whenever a manually-bought holding overlapped the wheel's configured 14 symbols — but with the two books in physically separate Alpaca accounts (`PA37XLNWDLB3` vs `PA3D36DVXSZ2`, verified in Phase 0), overlap is harmless: Alpaca cannot confuse a share held in one account for a share in the other. The guard only becomes meaningful under single-account consolidation, which is a deferred hypothetical. `config/strategy_registry.yaml` is therefore not needed. Accepted tradeoff: if consolidation ever happens, this guard has to be written then — under live-account pressure rather than now.

Phase 1 is therefore **five seams**, not six.

### Phase 2 — Covered-call engine

New `src/strategy/covered_call_engine.py` + `src/strategy/covered_call_state_manager.py` (simple state: HOLDING_STOCK → SELLING_CALLS; no put phase, no acquisition phase). **Stock entry is manual**: long positions are bought by hand via the Alpaca UI in the dedicated account; the bot automates only call selling, early-close, rolling, and assignment handling. Reconciliation therefore *adopts* every equity position it finds in the account as covered-call inventory — safe precisely because the account is dedicated, and it means manually added/trimmed share lots are picked up on the next cycle with no config change. Cost basis comes from Alpaca's `avg_entry_price` (`StockEntryCostBasisProvider`), which is reliable for purchased shares (the known `cost_basis=0` bug affects only assignment-acquired stock). Uncovered-shares handling: sell up to `floor(uncommitted_shares / 100)` contracts per underlying — the existing `ExecutionEngine` share guard (`:305-360`) already computes committed-share accounting. Odd lots (<100 residual shares) are simply left uncovered. Reuses `MarketDataManager.find_suitable_calls`, `CallSeller`, `CallRoller`, `ExecutionEngine`, `RiskManager`.

One policy decision surfaced by manual entry: whether the strike floor should be `avg_entry_price` (never sell below manual cost basis, mirroring wheel discipline) or a configurable floor (e.g. `max(avg_entry_price, pct_of_spot)`) — default to `avg_entry_price`, configurable per the existing `min_strike_price` parameter.

### Phase 3 — Deployment

Second Cloud Run service `covered-call-strategy` in `cloudbuild.yaml` from the same image: `STRATEGY_CONFIG=config/covered_call.yaml`, secrets `alpaca-api-key-cc`/`alpaca-secret-key-cc` (new paper account #2), own `STATE_STORAGE_BUCKET` prefix, dataset `covered_call`. Clone the Cloud Scheduler jobs (`/run`, `/monitor`, `/roll`, activities ingest) against the new service URL. `--max-instances=1` same as wheel.

### Phase 4 — Covered-call backtesting

**Revised 2026-07-18 after auditing the backtest-rebuild branch (`claude/backtesting-engine-overhaul-l15uj1`, FC-032).** The original premise here — "feed a `Strategy` interface requirement into the rebuild now" — is obsolete. What actually happened:

- `backtest_engine.py`, `portfolio.py`, `trade_simulator.py`, `historical_data.py`, and `cloud_storage.py` **were all deleted** in FC-032 Phase 0. The tree is now `data/` + `engine/` + `metrics/` + `reporting/`.
- The rebuild deliberately **replays live production strategy code** rather than abstracting over it. `engine/simulator.py:226` instantiates `WheelEngine` by name and drives `reconcile_positions()` / `run_strategy_cycle()` / `run_rolling_cycle()` directly. The stated rationale (`simulator.py:25-26`): *"Nothing in here reimplements strategy logic. If a rule is wrong, it is wrong in production too."*
- The abstraction seam the rebuild invested in is **under** the strategy, not around it: `BacktestAlpacaClient` (`engine/alpaca_adapter.py`) lets production code talk to a fake broker. The only `Protocol` in the tree is `OptionsDataProvider` (`data/provider.py:60`), a data-vendor seam.

**Consequence: this phase's dependency inverts.** A covered-call backtest is not blocked on a backtester interface — it is blocked on `covered_call_engine.py` (Phase 2) existing in production. Once it does, the backtest replays it the same way the wheel is replayed. Building a `Strategy` protocol before a second production strategy exists would be an abstraction with one implementor.

Work actually required in this phase, once Phase 2 lands:
1. Constructor injection at `simulator.py:226` — take a strategy factory instead of hardcoding `WheelEngine`. Blocker to resolve first: `simulator.py:332,337` reaches into `engine.put_seller`/`engine.call_seller` as concrete attributes, so `ExecutionEngine`'s signature leaks wheel structure into the seam. The strategy should expose its own execution callable instead of two named sellers.
2. A covered-call cycle definition parallel to `metrics/cycles.py` (no put phase; entry is manual, so a "cycle" starts at share acquisition, not at first option sold), and a scorecard variant of `metrics/fitness.py` that does not gate on `assignment_rate` or a completed wheel cycle.
3. Seed the sim with manually-held shares, since covered-call entry is exogenous — the wheel's flat-start assumption does not hold.

Note FC-032 Phase 5 (screen mode) is not started, so the backtest branch is still in flight.

## Risks & mitigations

- **Risk:** refactors regress the live wheel.
  - Mitigation: Phase 1 is behavior-preserving by construction (defaults = current values); wheel config untouched; canary deploy flow already exists; full pytest suite green as gate on each phase.
- **Risk:** client_order_id format change breaks idempotency across a deploy boundary (in-flight orders under old ids).
  - Mitigation: idempotency window is same-day; deploy after close, or have retry lookup check both formats for one day.
- **Risk:** state-blob path migration loses wheel state.
  - Mitigation: read-legacy-path shim + one-time copy script; state is also fully reconstructible via `reconcile_positions`.
- **Risk:** the two services drift (the fork-in-disguise failure mode).
  - Mitigation: one image, one `src/` tree, config-only divergence; CI builds a single artifact.
- ~~**Risk:** Alpaca paper-account facts wrong~~ **Retired 2026-07-18** — Phase 0 verified account isolation empirically against the live paper API. The unverified 3-paper-account cap no longer matters (we need 2, and owner declined to open a support ticket).
- **Risk:** the covered-call account is a **4x margin account** (`multiplier: 4`, $1,000,000 equity → $4,000,000 buying power) while the wheel account is 2x. `position_sizing.py` sizes against `buying_power`, so at equal equity the covered-call book would size ~2x larger than the wheel would — and a stock-holding strategy sized off margin buying power can buy more shares than it has cash to hold through a drawdown.
  - Mitigation: covered-call config sizes against `equity`, not `buying_power`. Assert this in Phase 2 config validation and cover it with a unit test.
- **Risk:** manual stock entry mid-session races the bot (shares bought while a call-sell batch is in flight, or shares sold manually out from under a short call → naked call).
  - Mitigation: bot recomputes uncommitted shares from live positions at the start of every cycle (existing `ExecutionEngine` guard); document the operator rule "never manually sell shares while short calls are open — buy-to-close the calls first"; add a startup/monitor check that flags `short_calls × 100 > shares` and alerts rather than trading.
- **Risk:** manual buys land as odd lots or with DCA'd blended `avg_entry_price` above current strikes, silently blocking all call sales.
  - Mitigation: log an explicit `skipped: strike_floor_above_market` decision (mirrors FC-029 drawdown-pause pattern) so idle inventory is visible on the dashboard, not a silent gap.
