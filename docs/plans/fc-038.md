# Plan: Two-pool execution selection — covered calls stop competing for cash they don't need

**FC entry:** `docs/FUTURE_CONSIDERATIONS.md` FC-038
**Plan file:** `docs/plans/fc-038.md`
**Status:** Draft
**Size:** M (production trading logic → high-stakes: two adversarial reviewers + confirmation pass required)
**Author:** Claude (investigation + adversarial review 2026-07-18)
**Last updated:** 2026-07-18

## Context

`docs/investigations/covered-call-starvation-2026-07-18.md` established, with an exact production reproduction, that the `/run` execution pipeline treats covered calls as if they required full cash collateral — in two places — and that this starved AAPL of covered calls for four trading days while its calls were the top-scored opportunities in every scan (~$75–$190/day of scanned premium foregone). The same mechanism throttles fleet throughput (~50–90 opportunities/day → 1–3 executions) and lets share-committed underlyings (GOOGL) win selection cycles they can never execute, wasting the slot each time.

The defects, concretely:

1. **Sizing gate** — `rank_opportunities` (`src/strategy/execution_engine.py:167-171`) calls `put_seller._calculate_position_size` for *every* opportunity type. Its BP cap (`buying_power // (strike*100)`, `src/strategy/put_seller.py:154`) silently drops calls whenever BP < strike×100 (observed: 7/14 runs at BP $621/$383 dropped everything, including three AAPL calls).
2. **Selection budget** — `select_batch` (`execution_engine.py:225-226`) deducts `strike × 100 × contracts` from buying power for calls. Covered calls consume shares, not cash.
3. **Wasted slots** — the available-shares check lives only in `execute_batch` (`execution_engine.py:305-360`), *after* selection has spent budget on an underlying that cannot execute.
4. **Silent drops** — neither stage logs per-opportunity drop reasons; the outage was invisible for four days.

An adversarial review confirmed the diagnosis and mandated the design below (its "REVISE" items are all incorporated; see the investigation doc's verdict section).

## Goals

- A covered call on an idle ≥100-share lot is always selectable regardless of cash buying power.
- Calls and puts stop competing for the same budget: **calls consume a per-underlying available-shares budget; puts consume the cash/BP budget.**
- Share-committed underlyings are excluded **at selection time**, not discovered at execution time.
- Every dropped opportunity logs a machine-queryable reason at ranking and selection stages.
- Behavior contract pinned by tests, including a golden-file replay of the Friday 2026-07-17 14:00 scan blob.

## Non-goals

- Roller repair (FC-039), journal labeling / log sink (FC-040), RiskManager consolidation or retirement (FC-014).
- Scanner scoring changes — `attractiveness_score` computation is untouched.
- Any change to put sizing, put ranking, or the DTE/delta/premium filters.
- Re-enabling drawdown-pause semantics on the scanner path (the cost-basis floor + delta range already exclude deep-drawdown symbols there; noted in the investigation).

## Proposed approach

### 1. Type-aware sizing in `rank_opportunities`

Route by `opp.get('type', 'put')`:

- **Puts:** unchanged — `put_seller._calculate_position_size` (BP-capped).
- **Calls:** new shares-based sizing: `contracts = available_shares(underlying) // 100`, where `available_shares = owned − committed_to_short_calls`, computed from the positions snapshot fetched once per run. If `contracts == 0`, drop **with a logged reason** (`selection_dropped`, `reason=insufficient_available_shares`). No BP involvement whatsoever.

Extract the committed-shares arithmetic that already exists inline in `execute_batch` (execution_engine.py:305-360) into a helper (e.g. `_available_shares(underlying, positions)`) used by both sizing and the final execution guard — one implementation, two call sites.

### 2. Two-pool `select_batch`

- Puts: greedy by ROI against `remaining_bp`, exactly as today.
- Calls: `collateral = 0` against BP; instead decrement a per-underlying share ledger initialized from the same positions snapshot. One-position-per-underlying dedup stays global across both types.
- **Ordering:** select calls first, then puts. Calls consume no cash, so this cannot starve puts; it removes any order-dependence between the pools. Within calls, rank by the scanner's `attractiveness_score` (already present on every scanner call opportunity; fall back to `premium / (strike × 100)` if absent). Within puts, ROI as today. Do **not** ship the naïve `roi = premium/collateral` with `collateral=0` — the existing guard turns that into `roi=0` and sorts calls last (adversarial-review trap #1).
- Log `opportunity_selected` / `selection_dropped` (with `reason` ∈ {`insufficient_available_shares`, `insufficient_buying_power`, `duplicate_underlying`, `sizing_failed`}) for every item, and add drop counts to the batch-selection summary event.

### 3. `execute_batch` keeps its guard

The available-shares check at execution time stays as defense-in-depth (positions can change between selection and execution). With selection now share-aware, its firing rate should drop to ~0; a firing is itself a signal worth the existing warning log.

## Critical files

- `src/strategy/execution_engine.py` — `rank_opportunities` (type-aware sizing), `select_batch` (two pools + logging), `execute_batch` (use shared `_available_shares` helper), new helper.
- `src/strategy/put_seller.py` — untouched (its sizing stays put-only); referenced for contract shape.
- `tests/test_execution_engine.py` — new coverage (see Verification).
- No config schema changes. No scanner changes. No endpoint changes.

## Reuse

- `execute_batch`'s existing committed-shares arithmetic (execution_engine.py:305-360) — extracted, not reimplemented.
- Scanner's `attractiveness_score` — already computed and stored in every call opportunity blob; becomes the call-ranking key instead of being ignored.
- Existing structured-logging helpers (`log_system_event` / `logger.info` with `event_category`/`event_type`) for the new drop events.

## Risks & mitigations

- **Risk:** call volume jumps immediately post-deploy (AAPL would get covered Monday; other idle lots too). This is the intended fix, but it changes live behavior at once.
  - Mitigation: cost-basis floor and delta-range filters are unchanged and remain the safety envelope (deep-drawdown symbols still naturally excluded — verified in the investigation for NVDA/AMZN). Deploy off-hours; watch the first two `/run` cycles.
- **Risk:** calls-first ordering plus zero collateral makes a *mispriced* call opportunity cheap to select.
  - Mitigation: selection only reorders **already-filtered** opportunities (delta, premium floor, cost-basis floor, liquidity all applied upstream in `find_suitable_calls`); no filter is loosened.
- **Risk:** the `not tradable` (Alpaca 42210000) failure loop can still waste a *call* slot on a genuinely available underlying.
  - Mitigation: out of scope to fully solve here; the per-contract `_failed_symbols` filter still applies, and with share-committed underlyings excluded at selection, the observed GOOGL loop specifically cannot recur. Residual risk documented.
- **Risk:** helper extraction regresses the execution-time guard.
  - Mitigation: guard behavior pinned by tests before refactor; confirmation review pass (mandatory per workflow) checks for exactly this class of regression.

## Open questions

- Should the scanner also stop emitting call opportunities for share-committed underlyings (cheap pre-filter, saves blob noise)? Harmless either way post-fix; lean yes as a follow-up commit, not a blocker.
- Cross-type cap: with calls first, a run can execute (calls + puts) up to the opportunity count — is any global per-cycle trade cap wanted? Config has `max_new_positions_per_cycle: null` today; leaving null preserves current semantics.
- `max_exposure_per_ticker` / `min_cash_reserve` remain unenforced anywhere (FC-014's question, answered 2026-07-18). Consolidation stays FC-014's scope — this plan deliberately does not sneak risk checks in.
