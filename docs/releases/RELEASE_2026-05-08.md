## Changes

### New Features

- **FC-029: Phase 1 wheel risk re-tune** ([docs/plans/fc-029.md](docs/plans/fc-029.md), commit `692f64e`, PR #34). Three complementary changes addressing the 3-loss-cycle pattern (-$9k share losses) found in the senior-trader review:
  - **R1**: `call_delta_range` `[0.30, 0.70]` → `[0.15, 0.25]`. Pushes call strikes 2–4% further OTM at any given moment; lowers assignment probability from 30–70% to 15–25%.
  - **R2**: `CallSeller._resolve_cost_basis_floor` deterministic source-order helper — reads `wheel_state.symbol_states[symbol]['stock_cost_basis']` (canonical, populated from put strike at OPASN time) → BQ lookup of last 90-day OPASN-put strike (handles silent assignments + cold starts; back-fills wheel_state) → Alpaca's `cost_basis` (last-resort fallback for non-wheel manual buys). When all three fail with shares > 0, the call write is blocked with `event_type=cost_basis_floor_unresolved`.
  - **R3**: drawdown pause — skip covered call writes when shares ≥ 5% below cost basis (`event_type=covered_call_drawdown_pause`). Bad/missing quote also defers (`event_type=covered_call_quote_missing`) instead of failing-open.
  - New `WheelStateManager.set_stock_cost_basis(symbol, value)` setter for BQ→state backfill.
  - Config: new `call_drawdown_pause_threshold: 0.05`.
  - 27 new vitest+pytest cases in `TestCallSellerCostBasisFloorFC029`; 253/253 total pytest green pre-merge.

## Key Decisions & Rationale

- **AMZN reconciliation pulled directly from Alpaca, not from BQ.** The user requested an end-to-end reconciliation against raw activity-feed data. Pulled all 76 AMZN activities from `/v2/account/activities` and walked them cycle-by-cycle. Confirmed dashboard math is correct given the data it's fed — the bug was purely data-completeness (FC-025 missing OPASN+OPTRD pair), not arithmetic. Documented in [docs/investigations/amzn-reconciliation.md](docs/investigations/amzn-reconciliation.md).

- **Strategy review framed as senior trader / financial analyst, not generic engineer.** The user explicitly asked for that lens. The persona caught domain-specific issues (asymmetric call vs put delta ranges, near-ATM call writes during downward moves, share-side capital loss vs option-side premium dynamics) that a generic engineer review would have missed. 12 prioritized recommendations across 4 phases — Phase 1 (R1+R2+R3) shipped as FC-029.

- **Cost-basis floor diagnosis: the user's challenge was right.** My initial framing was "dynamic erosion" — that the floor existed but slipped down ~$30 over a cycle. The user pushed back: "the actual per-share cost basis is the put strike of the assigning contract; we should use a static floor." Validated empirically: 100% of recent `call_sale_executed` events logged `stock_cost_basis: 0`. The floor wasn't dynamically eroding — it was non-functional from day one. The user's instinct was correct, and the fix was even simpler than initially proposed (the bot already captures the strike correctly; just read from `wheel_state` instead of Alpaca's broken field).

- **R1 chose `[0.15, 0.25]` over `[0.10, 0.20]` (symmetric with puts) or `[0.20, 0.30]`.** The narrower band centered around 0.20 delta gives a meaningful step-down from the prior 0.30-0.70 floor without going as conservative as put delta. Pairs naturally with R3's drawdown pause (when stock is below cost the bot pauses anyway, so there's no need to maximally suppress assignment probability via delta alone).

- **R2 source-order: `wheel_state` → BQ → Alpaca, not the simpler "wheel_state only".** The simpler "trust wheel_state, crash if missing" was rejected because cold-start recovery is real. The 3-source chain handles: (a) normal operation (wheel_state hit), (b) cold start (BQ recovers from `trades_from_activities`), (c) non-wheel manual buy (Alpaca's value works correctly for stock acquired via market order). Each source has a logged failure mode so silent bypass is now observable.

- **R3 threshold of 5% chosen empirically; per-symbol override deferred.** Static threshold acknowledged as imperfect — AMD's daily ATR is ~3-4% (5% is one and a half daily moves), AMZN's ~2%, IWM's ~1%. Right architecture is `k × symbol_30d_realized_vol`, but that adds tuning surface area without baseline data. Shipped static 5% with config-only override slot pre-wired so per-symbol tuning is doc-only; defer the dynamic version to FC-030+ once the baseline exists.

- **Single-pass deploy, no feature flag.** The second reviewer flagged this as a process concern. Rejected for FC-029: we're on paper trading; rollback is `git revert + redeploy` (~3 min). Feature-flag overhead for a paper-trading change is overkill. Would re-evaluate for live capital.

- **`~/CLAUDE.md` upgrade applied immediately, not retroactively.** The workflow upgrade was published mid-session. Decided NOT to re-run FC-029 review under the new rules (that review's findings were already addressed). Applied it to the second reviewer of FC-029 — a real test of "does the new process actually catch what the old one missed?" Result: it did. 4 HIGH-severity issues that would have shipped to a real-money trading bot otherwise.

Bundling into FC-029 would have expanded scope. Filed as a separate FC; can ship after Phase 1 baseline observed.

## Discoveries

- **Alpaca paper-engine returns `cost_basis = 0` for stocks acquired via option assignment.** Confirmed empirically across 8/8 recent `call_sale_executed` events. Not specific to silent-exercise — happens for normal (non-silent) OPASN events too. The most likely cause: Alpaca computes `cost_basis = qty × avg_entry_price`, and `avg_entry_price` for assigned shares is set to 0 (no cash paid at acquisition; the cash flow is recorded in the put-assignment ledger separately). Some brokers (Schwab, Fidelity) compute as `strike − premium received` per IRS §1234. Alpaca's paper engine appears not to. Out of our control upstream; treat the field as advisory/fallback only.

- **AMZN cycle 2 ($1,333 cycle P&L) had a 62-day idle window inside it (Feb 6 → Apr 10).** No covered-call activity for 62 days while shares were silently held. Per the AMZN reconciliation, this was the cost-basis floor (when "working") blocking calls because every delta-range strike was below the $240 cost basis. Pre-FC-029 the bug masked this by always returning 0 floor, so calls happened anyway. Post-FC-029 the drawdown pause makes this an explicit, observable decision instead of a side effect.

- **Two-reviewer process catches a meaningfully different class of bug.** First reviewer was generic-engineer-focused; caught test gaps and structural issues. Second reviewer was domain-specific (options trader / quant risk); caught operational failure modes (BQ project arg, fail-open quote handling, cold-start latency, stale-data risk) and architectural critiques (regime-blind static parameters, no feature flag). Different personas surface different findings — confirmed by data on first invocation.

- **The 3 loss cycles share a parameterizable failure mode.** AMD 11-17 (-$1,925), AMZN 11-04 (-$443), UNH 10-30 (-$532) all have: stock dropped 5–16% between assignment and called-away, bot was called away below assignment strike, total cycle premium captured was less than the share-side capital loss. This is not random — it's the consequence of `call_delta_range = [0.30, 0.70]` + non-functional cost-basis floor. The 3-cycle pattern was the "smoking gun" that validated FC-029's premise. Future similar cycles will be visible because R3 fires the pause + the floor blocks sub-cost calls.

- **The wheel achieved 54% of B&H dollar P&L across 7 symbols.** Caveats apply (capital efficiency, risk-adjusted returns), but within the strategy's design envelope, ~$9,000 of the gap traces to the 3 loss cycles. Eliminating that pattern doesn't close the entire gap, but it shifts the structural bias.
